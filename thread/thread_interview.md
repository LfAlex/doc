# 一、基础概念

## 1.1 进程和线程的区别？为什么线程叫轻量级进程？协程/纤程是什么？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：上下文切换保存什么 → LWP 与 task_struct → 协程和虚拟线程关系
> **风格**：字节会打穿到页表/TLB；阿里爱接"你们线上线程数多少、为什么"

**答案：**
进程是操作系统**资源分配的最小单位**，拥有独立虚拟地址空间、页表、文件描述符、信号、堆；进程间完全隔离，切换需换页表、刷 TLB，开销巨大。
线程是**OS 调度的最小单位**（LWP 轻量级进程）；同进程内所有线程共享地址空间、堆、全局变量、文件句柄；线程私有：虚拟机栈、PC 程序计数器、寄存器上下文、TLS。

为什么叫"轻量级"：创建不重新分配地址空间，切换只换寄存器与栈、不换页表，创建/切换/销毁成本远低于进程。

**延伸：**
- 协程：用户态调度，OS 无感知；分有栈/无栈；Java 虚拟线程属 JVM 托管的有栈协程
- IPC：管道、消息队列、共享内存、信号、Socket，都需内核介入
- 线程通信：共享内存（受 JMM 约束）、等待唤醒、队列，开销更低
- 一个进程至少一个主线程

## 1.2 并发和并行的区别？单核 CPU 能并发吗？
> **🟥 S ｜ 字节 ★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：时间片轮转 → 上下文切换代价 → 并发不等于高性能
> **风格**：多为开场热身题，答得干净利落即可，别在这里耗时间

**答案：**
并行：多任务**同一时刻**同时执行，依赖多核。
并发：多任务在**一段时间内交替执行**，靠时间片轮转，宏观同时、微观串行。
单核**可并发、不可并行**。

**延伸：** 并发≠高性能；无阻塞任务时，并发反而因切换和竞争降低吞吐。

## 1.3 Java 创建线程几种方式？start() 和 run() 的本质区别？为什么不推荐直接 new Thread？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：start0 是 native → JVM 创建 LWP → 为何 Callable 不能直接给 Thread
> **风格**：三家必问；字节会顺接"那线程池怎么替代它"

**答案：**
四种：继承 Thread 重写 run；实现 Runnable 传 Thread；Callable+FutureTask（有返回值、可抛受检异常）；线程池提交。

- `run()` 是普通方法，直接调用在**当前线程同步执行**，不创建 OS 线程
- `start()` 调 native `start0()`，触发 JVM 调 OS API 创建 LWP，调度器分配时间片后才回调 run()

不推荐直接 new Thread：创建是系统调用成本高；无管控易耗尽句柄/内存；无监控与拒绝策略；线程数不可控引发上下文切换风暴。

**延伸：** FutureTask 同时实现 Runnable 和 Future，是 Callable 与 Thread 的适配器。

## 1.4 Java 线程 6 种状态；sleep / wait / yield / join 区别
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：RUNNABLE 为什么包含就绪 → wait 为何释放锁 → 中断后状态变化
> **风格**：**最容易翻车的一道**。答不出"RUNNABLE ≠ OS 运行态"，字节会直接判定是背的

**答案：**
`NEW → RUNNABLE → BLOCKED / WAITING / TIMED_WAITING → TERMINATED`

⚠️ 核心考点：**Java RUNNABLE ≠ OS 运行态**，它把 OS 的"就绪（在调度队列排队）+ 运行"合并成一个状态，因为 JVM 无法感知 OS 内部细分。

- **BLOCKED**：仅竞争 `synchronized` 监视器锁失败，进 EntryList
- **WAITING**：无限等待：`wait()`、`join()`、`park()`
- **TIMED_WAITING**：带超时：`sleep()`、`wait(n)`、`join(n)`、`parkNanos()`

对比：
1. sleep：Thread 静态方法；**不释放锁**；超时自动回 RUNNABLE
2. wait：Object 方法；必须持锁；**调用即释放锁**；进 WaitSet；需 notify 唤醒
3. yield：让出时间片回就绪队列；**不释放锁**；仅提示调度器，可被忽略
4. join：等待目标线程结束；底层 wait 循环；阻塞当前线程，**不释放当前线程持有的锁**

**延伸：** yield 在很多 OS 上几乎无效，别拿它做业务顺序控制。

## 1.5 stop()、suspend() 为何废弃？interrupt 中断机制
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：interrupt 与 interrupted/isInterrupted 区别 → 阻塞态 vs 运行态响应差异
> **风格**：常接"那你怎么优雅停线程"，答出"标志位+interrupt"即可

**答案：**
- stop()：暴力终止，立刻释放所有监视器锁，共享数据被破坏，无清理机会
- suspend()：挂起但**不释放锁**，极易死锁

interrupt 是协作式中断，只打标记不杀线程：
- sleep/wait/join 阻塞时 → 抛 InterruptedException 并**清除中断标记**
- park 阻塞时 → 直接返回，**保留中断标记**
- 运行中 → 仅置标记位，需业务轮询 `isInterrupted()`

**延伸：** `interrupted()` 静态方法读取并清除；`isInterrupted()` 实例方法只读不清除。

## 1.6 守护线程 Daemon
> **🟨 B ｜ 字节 ★ ｜ 阿里 ★ ｜ 腾讯 ★**
> **风格**：偶尔带过，答清"JVM 退出规则"即可

**答案：** 仅 JVM 层标记，不是 OS 层概念。所有非守护线程结束，JVM 直接退出并杀掉守护线程，不等其跑完。GC 线程即守护线程。

# 二、JVM + OS 底层线程模型

## 2.1 N:1 / 1:1 / M:N 线程模型？HotSpot 默认是哪种？优缺点
> **🟧 A ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：为何 Java 放弃绿色线程 → 虚拟线程属于哪种 → 1:1 的代价具体是什么
> **风格**：字节顺接虚拟线程，阿里爱问"为什么不做 M:N"

**答案：**
- **N:1（绿色线程）**：多用户线程映射 1 个 OS 线程，用户态调度，切换快；致命缺陷：**一个阻塞全阻塞**；JDK1.2 前方案，已废弃
- **1:1（平台线程，HotSpot 默认）**：1 个 Java Thread 绑 1 个 OS LWP，Linux 走 `pthread_create`，由 OS 内核调度；优点：多核并行、互不阻塞；缺点：创建成本高、栈固定、切换开销大
- **M:N（JDK21 虚拟线程）**：大量虚拟线程映射少量载体线程，JVM 调度，阻塞时卸载归还载体线程

**延伸：** Linux 下 LWP 本质是 task_struct，TGID 相同即同进程；`ps -L` 可看 LWP。

## 2.2 new Thread() → start() → 执行 → 销毁：三层完整流转
> **🟧 A（接近 S） ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：线程栈谁分配多大 → 退出时线程对象何时回收 → 队列在哪几层
> **风格**：**字节二面题眼**。能讲成链路而不是罗列，直接拉开差距

**答案：**
**① Java 层**：`new Thread()` 堆创建对象，初始化 name/target/priority/daemon，`threadStatus=NEW`；**此时无 OS 线程、无栈**
**② Java 调用 start() → native start0()**
**③ JVM 层**：`JVM_StartThread`
  - 分配 Java 线程栈（`-Xss`）、JNIEnv、TLS
  - 封装线程入口 → 调 `os::create_thread`
**④ OS 层**：
  - `pthread_create` → 内核 `clone()`
  - 创建 task_struct（PCB），分配**内核栈**
  - LWP 入 CFS 红黑树就绪队列
  - 调度器分配时间片，执行入口 → 回调 JVM → 进入 Java run()
**⑤ 运行期**：正常执行 / 阻塞 / 抛异常
**⑥ 退出**：
  - JVM 回调 UncaughtExceptionHandler
  - 释放 Java 栈、TLS；通知 OS 销毁 LWP
  - OS 回收 task_struct，移出调度队列
  - **Thread 对象留在堆中成为普通对象，等 GC**

**队列分布（必记）：**
| 层级 | 队列 |
|---|---|
| OS | CFS 就绪队列（红黑树） |
| synchronized | EntryList（锁阻塞）、WaitSet（等待集） |
| AQS | CLH 双向同步队列、Condition 条件队列 |

**延伸：** OS 线程销毁 ≠ Thread 对象回收，两者生命周期完全解耦，这是高频追问点。

## 2.3 上下文切换是什么？保存什么？何时触发？怎么观测？
> **🟧 A ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★**
> **追问链**：自愿 vs 非自愿切换 → 该看哪个指标 → 切换过多为什么 sys 高
> **风格**：阿里几乎必接线上案例；字节要求说得出 perf/pidstat

**答案：**
保存：通用寄存器、PC、栈指针、浮点寄存器；进程切换还要换页表、刷 TLB。
触发：时间片耗尽抢占、阻塞（锁/IO/park/sleep）、主动 yield、高优先级抢占。
观测：`pidstat -w`、`vmstat`、`perf sched`。

**延伸：** 分**自愿**（主动阻塞）和**非自愿**（被抢占）；排查优先看非自愿，"非自愿切换暴涨=CPU 竞争激烈"。

## 2.4 TLS / 用户态内核态切换 / futex
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★ ｜ 腾讯 ★**
> **风格**：futex 是字节偏爱的点；讲清"无竞争走用户态、有竞争才进内核"

**答案：**
TLS：每线程私有区，JVM 存栈基址、JNIEnv、线程 ID、异常链、信号上下文。
用户态→内核态：系统调用、中断、缺页异常。
futex：Linux 快速用户态锁，无竞争时用户态 CAS，竞争才陷入内核挂起；synchronized 重量级锁、LockSupport 底层均依赖它。

## 2.5 线程异常退出流程、UncaughtExceptionHandler
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：线程池任务异常看不见日志怎么办
> **风格**：三家都倾向在线程池语境下问，属于"踩坑题"

**答案：**
run 抛未捕获异常 → JVM `dispatchUncaughtException` → 优先线程自身 handler，否则线程组 handler → 线程终止，不影响其他线程。

**延伸：** 线程池 execute 提交异常抛出、线程退出、池补新线程；submit 异常存 Future、线程复用。建议 ThreadFactory 统一挂 handler，避免异常静默。

# 三、JMM

## 3.1 JMM 是什么？和 JVM 运行时数据区的区别？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：JMM 是规范还是实现 → HotSpot 怎么落地的
> **风格**：**极易混淆题**，答错说明概念没扎根

**答案：**
JMM 是**抽象并发规范**，不是物理内存；定义多线程共享变量读写规则，解决可见性/原子性/有序性，屏蔽不同 CPU 差异。
JVM 运行时数据区（堆、虚拟机栈、本地方法栈、PC、方法区）是**内存划分**，与并发无关。

一句话：**JMM 管共享变量读写语义；内存分区管内存分配位置。**

**延伸：** JMM 只约束共享变量；栈上局部变量无线程安全问题。

## 3.2 可见性 / 原子性 / 有序性，各自被什么破坏？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：i++ 为什么不是原子 → 怎么保证每个特性
> **风格**：基础判断题，答完整即可

**答案：**
- 可见性：CPU 缓存导致修改只在本地缓存，其他线程不可见
- 原子性：i++ 是读-改-写三步，可被中断
- 有序性：编译器/JIT 重排、CPU 乱序；单线程无影响，多线程无同步会出错

**延伸：** 单线程内重排遵守 as-if-serial，不改变语义；并发 bug 难复现是因为重排是概率性的。

## 3.3 happens-before 规则
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★**
> **追问链**：要求举例而不是背条文 → 没有 HB 约束会怎样
> **风格**：背六条不给分，**能举 DCL 或 start/join 的例子才给分**

**答案：**
不是执行先后，是**可见性保证**：A HB B，则 A 的修改对 B 可见。
六条：程序顺序、监视器锁（unlock HB 后续 lock）、volatile（写 HB 后续读）、start（start HB 线程内全部）、join（线程内全部 HB join 返回）、传递性。

**延伸：** 无 HB 约束的两个操作，JMM 允许任意重排——这是并发 bug 的根源。

## 3.4 volatile 原理、内存屏障、DCL 为何必须 volatile
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：volatile 保证可见性 → 靠什么 → MESI → MESI 能防重排吗 → 内存屏障 → StoreLoad 为何最贵
> **风格**：**全套里追问链最长的一题**，字节必打三层；DCL 是阿里招牌题

**答案：**
volatile 两点：**可见性 + 禁止重排；不保证原子性**。
底层四类屏障：LoadLoad、StoreStore、LoadStore、StoreLoad；volatile 写后插 StoreLoad（开销最大，需清空写缓冲并等待）。

DCL：`new Singleton()` 三步——分配内存 → 初始化 → 引用赋值；JIT 可能重排为分配 → 赋值引用 → 初始化，导致其他线程拿到**半初始化对象**；volatile 禁止该重排。

**延伸：** volatile 不能用于 i++；适合状态标记、开关、DCL；计数应用 Atomic。

## 3.5 volatile 不保证原子性、适用场景
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> 常与 3.4 合并出现，属同题的第二问

**答案：** 复合操作需锁或 Atomic；volatile 适合标志位、一次性安全发布。

## 3.6 MESI 缓存一致性协议、伪共享
> **🟨 B ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★**
> **追问链**：缓存行多大 → 伪共享怎么产生、怎么解决 → @Contended 原理
> **风格**：**字节的加分题**，答出来明显区分层级；阿里会接"线上性能问题"

**答案：**
MESI 四态：Modified、Exclusive、Shared、Invalid；总线嗅探维护一致性。volatile 可见性依托 MESI，但 MESI 防不住指令重排，故仍需屏障。

伪共享：多个独立变量落在同一 64 字节缓存行，改一个导致整行失效，其他变量频繁失效，性能骤降；`@sun.misc.Contended` 填充缓存行解决。

**延伸：** 高并发计数器、metrics 统计最易踩；大量 volatile 并发写还会引发总线风暴。

## 3.7 as-if-serial 语义
> **🟩 C ｜ 字节 ★ ｜ 阿里 ★ ｜ 腾讯 ★**
> 极少单独问，通常作为 3.2/3.3 的补充

**答案：** 无论怎么重排，单线程执行结果不能改变。

# 四、锁体系

## 4.1.1 synchronized 三种修饰位置，锁对象是谁？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：锁对象能用包装类吗 → 为什么不能为 null
> **风格**：送分题，答错很掉分

**答案：** 实例方法→this；静态方法→当前类 Class 对象；代码块→括号内对象。

**延伸：** 别用包装类常量作锁（Integer 常量池会意外共用锁）；锁对象不能为 null。

## 4.1.2 锁升级：偏向锁 → 轻量级锁 → 重量级锁，Mark Word
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：MarkWord 各状态存什么 → 偏向锁怎么撤销 → 现在还开吗 → 为什么官方要废弃
> **风格**：**三家必问**。字节要位布局；阿里爱问"生产上到底开不开、怎么权衡"

**答案：**
Mark Word 记录锁状态、GC 分代年龄、偏向线程 ID；锁**只能升级不能降级**。

1. **偏向锁**（无竞争）：首次加锁把线程 ID 写入 Mark Word，同线程再来直接通过，竞争到来触发撤销
2. **轻量级锁**（少量交替竞争）：栈帧建 Lock Record，CAS 把对象头指向锁记录，自旋 CAS 抢锁，失败膨胀；自旋在**用户态**不进内核
3. **重量级锁**（大量竞争）：膨胀为 futex，抢不到进内核阻塞挂 EntryList，释放时唤醒，内核切换开销大

配套优化：自适应自旋、锁消除（逃逸分析）、锁粗化。

**延伸：** 偏向锁撤销有成本，高竞争场景很多团队关闭；**不存在锁降级**，网上"锁降级"说法是错的。

## 4.1.3 自旋锁、自适应自旋、锁消除、锁粗化
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：逃逸分析怎么判定 → 锁消除对业务有什么实际收益
> **风格**：能举"StringBuffer 局部变量被消除锁"这种例子效果最好

**答案：** 自旋：用户态 CAS 循环，避免入内核；自适应自旋：按上次成功率动态调次数；锁消除：逃逸分析发现锁对象不逃逸直接去锁；锁粗化：连续多次加锁合并为一次。

## 4.1.4 synchronized 可重入？公平？可中断？
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：可重入底层怎么实现（计数器）

**答案：** ✅ 可重入（计数器累加递减）；❌ 非公平；❌ 不可中断（interrupt 只置标记位）。

## 4.1.5 为什么"锁降级"不存在？
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★**
> **风格**：**测你有没有被博客带偏**，答"官方没有锁降级"是加分

**答案：** JDK 锁升级是单向的，重量级锁不会退回轻量级/偏向锁，官方也没有锁降级机制。网上说的"锁降级"多是把读写锁的"写锁→读锁"降级混为一谈。

## 4.2.1 synchronized vs Lock 区别
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：JDK6 优化后还有必要用 Lock 吗 → 你怎么选

**答案：**
1. synchronized 是 JVM 关键字，自动加解锁，异常自动释放；Lock 是 API，必须 finally 里 unlock
2. 前者底层监视器，后者 AQS
3. Lock 支持 lockInterruptibly、tryLock 超时
4. Lock 支持多 Condition；synchronized 只有单个 WaitSet
5. ReentrantLock 可选公平/非公平；synchronized 只能非公平
6. Lock 可尝试拿锁；synchronized 不行

**延伸：** JDK6 后两者性能差距很小，**选型看功能需求（超时/中断/多条件）而非性能**。

## 4.2.2 AQS：state、CLH 双向队列、acquire/release 全流程
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：为何是双向 → Node 存线程吗 → 为何前驱是 head 才重试 → 何时 park
> **风格**：**最能分层的一题**。能讲到 Node 与 park 的细节，基本 A 以上

**答案：**
三要素：
1. `state`：同步状态 int；独占锁 0/1；读写锁高 16 位读、低 16 位写
2. **CLH 双向同步队列**：抢锁失败封装 Node 入队，自旋 + park
3. **Condition 单向条件队列**：await 从同步队列迁入；signal 迁回同步队列尾部

acquire：CAS 尝试 → 失败入队 → 循环判断前驱是否 head 才重试抢锁 → 仍失败则 park
release：释放 state，unpark 后继

**延伸：** Node 不存线程本体，只存线程引用；AQS 是模板方法，子类实现 tryAcquire/tryRelease；它是所有 JUC 同步器的骨架。

## 4.2.3 独占模式 vs 共享模式
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：读写锁读锁为什么算共享 → Semaphore 用哪种

**答案：** 独占：仅一线程持 state（ReentrantLock）；共享：多线程同时获取（CountDownLatch、Semaphore、读锁）。

## 4.2.4 ReentrantLock 公平 vs 非公平
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：公平锁为何吞吐低 → 生产到底用哪个
> **风格**：阿里爱问取舍；要答"公平锁不是绝对公平，只是保证排队"

**答案：** 非公平：先 CAS 抢，抢不到才入队，新线程可插队；吞吐高、有饥饿风险；默认。公平：先查队列有无等待者，有则直接入队；严格 FIFO，吞吐低。

## 4.2.5 ReentrantReadWriteLock、锁降级、为何不能锁升级
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：读锁为什么不能 newCondition → 写多场景怎么办

**答案：** 读共享写互斥；**锁降级**（写→读→释放写）允许，防写饥饿；**锁升级会死锁**，多线程持读锁互相等写锁。

**延伸：** 读锁不支持条件变量；写多场景读写锁性能差，考虑 StampedLock 或分段。

## 4.2.6 StampedLock 乐观读
> **🟩 C ｜ 字节 ★ ｜ 阿里 ★ ｜ 腾讯 ★**
> 低频，但知道"不可重入、用错会死锁"是加分

**答案：** JDK8，乐观读不加锁拿版本戳，读完校验戳是否变化；适合读极多写极少；有数据不一致风险需校验；**不可重入**。

## 4.2.7 Condition 与 wait/notify 对比，signal 语义
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：signal 后线程立刻运行吗 → 为什么要两个队列（生产/消费分离）

**答案：** wait/notify 绑对象监视器，一个对象仅一个 WaitSet；Condition 绑 Lock，一把锁可多个条件队列，实现精准唤醒。await 释放锁进条件队列；signal 仅把节点迁回同步队列，**不立即运行**。

## 4.3.1 CAS 原理、ABA 问题、缺点与解决
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：ABA 实际会造成什么业务问题 → 自旋的代价

**答案：** CAS 是 CPU 原子原语，比较后再交换。ABA：值 A→B→A，CAS 认为未变但实际被改过；用 `AtomicStampedReference` 加版本号解决。缺点：自旋耗 CPU、只能保证单变量原子、ABA。

## 4.3.2 Unsafe 与底层原子指令
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★ ｜ 腾讯 ★**
> 通常只在字节深挖时出现

**答案：** AtomicInteger 底层 Unsafe + CAS；Unsafe 可直接操作内存、park/unpark；JDK9 后不推荐直接使用。

## 5.1 wait 为何必须在 synchronized 内调用？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：不在里面会抛什么异常 → WaitSet 是什么结构

**答案：** wait 本质是把当前线程加入监视器 WaitSet 并释放锁；WaitSet 是监视器内部结构，只有持锁才能操作。否则抛 `IllegalMonitorStateException`。

## 5.2 虚假唤醒，为何必须 while 不用 if？
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：虚假唤醒是 Java 的 bug 吗 → OS 层面为什么会这样

**答案：** 是 POSIX 条件变量规范特性，OS 可能在无 notify 时唤醒线程；if 唤醒后不再判条件直接执行会出错；while 循环重判，不满足继续 wait。

## 5.3 LockSupport.park/unpark vs wait/notify
> **🟧 A ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：为什么"先 unpark 后 park"也生效 → 许可为何不累加
> **风格**：字节喜欢这个反直觉点

**答案：**
1. 不需持有锁
2. unpark 是发许可，许可最多 1 个，**先 unpark 后 park 也生效**（最大差异）；wait 必须先 wait 再 notify
3. park 响应中断，中断标记为 true 时直接返回不抛异常
4. 底层 futex；AQS 阻塞即靠它

**延伸：** 多次 unpark 等价一次，许可不累加。

## 5.4 线程间通信方案汇总

> 属归纳题，通常作为综合问答

**答案：** 共享变量（JMM）、wait/notify、LockSupport、Condition、阻塞队列、同步工具类（Latch/Barrier/Semaphore）。

# 六、线程池（三家共同的重中之重）

## 6.1 为什么用线程池？
> **🟥 S ｜ 字节 ★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> 快速过即可，别在这里展开太久

**答案：** 线程复用避免频繁创建销毁的系统调用开销；控制最大并发保护服务器；统一管控（拒绝策略、回收、监控、命名）；解耦任务提交与执行。

**延伸：** 任务极短时线程池额外开销可能不如直接创建；核心是资源池化思想。

## 6.2 七大参数 + 执行流程（顺序不能错）
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：核心线程何时创建（懒加载）→ 队列满了但核心线程空闲怎么办
> **风格**：**顺序错一步就扣分**，必须背到条件反射

**答案：** corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、handler、threadFactory。

流程：
1. 运行线程数 < corePoolSize → 建核心线程
2. ≥ corePoolSize → 入阻塞队列
3. 队列满 → 建非核心线程
4. 总线程数达 max → 触发拒绝策略

**延伸：** 核心线程默认不回收（`allowCoreThreadTimeOut=true` 才回收）；核心线程懒加载，可 `prestartAllCoreThreads` 预热。

## 6.3 4 种拒绝策略 + 自定义策略
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：你们线上用哪个 → 为什么不用 CallerRuns
> **风格**：阿里会追问真实生产配置

**答案：** AbortPolicy 抛异常（默认）；DiscardPolicy 静默丢弃；DiscardOldestPolicy 丢队首老任务重试；CallerRunsPolicy 提交线程自己跑，形成回压。

**延伸：** CallerRuns 天然限流，适合流量平缓；高吞吐系统通常自定义（落 MQ、持久化、降级返回）。

## 6.4 Executors 为何被阿里规范禁止
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★（招牌） ｜ 腾讯 ★★★**
> **追问链**：那你自己怎么创建 → 队列该选有界还是无界

**答案：** newFixed/newSingle 用无界 LinkedBlockingQueue，任务堆积 OOM；newCached 的 max=Integer.MAX_VALUE，无限建线程句柄耗尽。

**延伸：** 不是绝对禁用，简单脚本/测试可用；生产手动 new ThreadPoolExecutor 并给有界队列。

## 6.5 execute vs submit，异常行为差异
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：为什么 submit 的异常经常"看不见" → 线程会不会死

**答案：** execute 无返回、异常直接抛、线程退出；submit 返回 Future、异常封装其中，get 才抛、线程复用。

**延伸：** 生产常见坑：submit 后忘记 get，任务失败无日志。建议任务内 try-catch 或自定义 ThreadFactory 挂 handler。

## 6.6 5 种状态，shutdown vs shutdownNow
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：shutdownNow 能保证任务停下吗

**答案：** RUNNING / SHUTDOWN（不收新任务，队列跑完）/ STOP（中断执行中，丢队列）/ TIDYING / TERMINATED。shutdownNow 只是发中断，**任务不响应中断则停不下来**。

## 6.7 参数怎么设：CPU/IO 密集公式及局限性
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：阻塞系数怎么算 → 你们线上设多少、依据是什么
> **风格**：**只报 2N 会被继续打**。标准高分路径：公式 → 阻塞系数 → 必须压测 → 看下游承载力

**答案：**
经验值：CPU 密集 = 核数 + 1；IO 密集 = 核数 × 2。
真实公式：`线程数 = 核数 / (1 - 阻塞系数)`，阻塞系数 = 阻塞时间 / 总耗时。

**延伸：** 公式只是起点。RPC/DB 阻塞高的场景线程数可以很大，但真正上限取决于**下游承载力**——线程数超过下游容量只会把压力转化成排队和超时。必须压测。

## 6.8 核心线程超时回收、预热
> **🟨 B ｜ 字节 ★ ｜ 阿里 ★★ ｜ 腾讯 ★**
> 属于细节题

**答案：** 默认不回收，`allowCoreThreadTimeOut(true)` 可回收；`prestartAllCoreThreads()` 预热避免首请求抖动。

## 6.9 阻塞队列选型
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：LinkedBlockingQueue 为什么并发更高 → SynchronousQueue 用在哪个池

**答案：**
- ArrayBlockingQueue：数组、有界、单锁
- LinkedBlockingQueue：链表、可无界、**读写双锁分离**，并发更高
- SynchronousQueue：不存元素，put 必须等 take（newCached 底层）
- DelayQueue：按到期时间出队，做定时/超时关单

## 6.10 Scheduled：fixedRate vs fixedDelay
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：任务执行超过周期会怎样（并发跑，需幂等）

**答案：** fixedRate 按任务**开始时间**固定周期，任务慢会追赶；fixedDelay 按**上次结束时间**延时，耗时不影响间隔。

## 7.1 CountDownLatch vs CyclicBarrier

Barrier：可 reset 复用，N 个线程互相等全部到齐才放行，支持 barrierAction（到齐后优先执行一个任务）

## 7.3 CompletableFuture 编排、commonPool 的坑
> **🟧 A ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★★★（微信系偏爱）**

## 7.4 ForkJoinPool 工作窃取
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★ ｜ 腾讯 ★**

# 八、ThreadLocal

## 8.1 底层结构：Thread → ThreadLocalMap → Entry
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：为什么放在 Thread 里而不是 ThreadLocal 里（答案：生命周期与线程一致、避免竞争）

**答案：** Thread 对象内部持有 ThreadLocalMap，Entry 的 key 是 ThreadLocal 实例（弱引用），value 是业务数据。

## 8.2 弱引用 / 强引用 / 内存泄漏根因，线程池场景怎么办
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★（微信系尤其看重）**
> **追问链**：弱引用解决了什么、没解决什么 → 线程池里怎么安全用 → 为什么必须 remove

**答案：**
弱引用让 key 在 ThreadLocal 无外部强引用时可被 GC；但 **value 是强引用**，线程长期存活（池化复用）时 key 被清而 value 残留形成脏 Entry → 内存泄漏。**用必 remove()。**

线程池场景额外风险：线程复用导致**脏数据串号**（上一个请求的上下文被下个请求读到），这是比内存泄漏更常见的线上事故。

## 8.3 InheritableThreadLocal 与线程池失效
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：异步链路怎么传 traceId（答 TTL / 手动透传）

**答案：** 创建子线程时复制父线程 map；线程池中线程是预先创建复用的，复制时机早已过去，故失效。异步场景需 TTL（TransmittableThreadLocal）或显式透传。

# 九、并发容器

## 9.1 HashMap 为何线程不安全
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**

**答案：** JDK7 并发扩容可能形成链表环（死循环）并丢数据；JDK8 结构改为尾插不再成环，但仍会丢数据、size 错乱。

## 9.2 ConcurrentHashMap：JDK7 分段锁 vs JDK8 CAS+synchronized
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：JDK8 锁粒度是什么 → 扩容怎么协助 → size 怎么算

**答案：**
JDK7：Segment 分段锁，每段一把 ReentrantLock，并发粒度=段
JDK8：废弃分段，数组+链表+红黑树，**CAS + synchronized 锁桶头节点**，粒度细到桶；支持 helpTransfer 协助扩容；size 为分段累加估算值。

**延伸：** 弱一致性，get 不加锁可能读到旧值；`containsKey`+`put` 的复合操作仍非原子。

## 9.3 CopyOnWriteArrayList 场景与代价
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**
> **追问链**：为什么适合读多写少 → 内存代价多少

**答案：** 写时复制整份数组再替换引用（volatile 引用），读不加锁；弱一致性读到旧快照；写开销大、内存可能翻倍；适合读极多写极少（监听器列表、配置快照）。

## 9.4 CHM 弱一致性与复合操作陷阱
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**

**答案：** get 不加锁；size 是估算；复合操作需 computeIfAbsent / merge 等原子 API。

# 十、死锁与故障排查

## 10.1 死锁四条件、jstack 排查、避免
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：你实际遇到过吗 → 怎么定位锁持有者
> **风格**：阿里最爱接真实案例，准备好一个能讲的场景

**答案：** 互斥、持有并等待、不可剥夺、循环等待；四者同时满足才死锁。排查：`jstack pid`，找 `Found one Java-level deadlock`。避免：统一加锁顺序、tryLock 超时、破坏持有等待。

## 10.2 活锁 vs 饥饿
> **🟨 B ｜ 字节 ★ ｜ 阿里 ★★ ｜ 腾讯 ★★**

**答案：** 活锁：反复重试一直失败，无阻塞但 CPU 高（互相谦让）；饥饿：长期拿不到资源（非公平锁、写锁饥饿）。

## 10.3 CPU 100% 排查全链路
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★**
> **追问链**：怎么区分是业务线程还是 GC 线程 → 什么栈说明是自旋
> **风格**：**字节最爱的实操链路题**，要求说得出具体命令

**答案：**
`top` 找 pid → `shift+H` 看线程 tid → `printf "%x" tid` 转 16 进制 → `jstack pid` 搜该 tid → 定位栈：死循环 / CAS 自旋 / GC。

**延伸：** 先分清高 CPU 是业务线程还是 GC 线程；GC 高看 GC 日志与回收频率；业务线程高看是否死循环或锁自旋。

## 10.4 服务无响应 / 线程全阻塞排查
> **🟧 A ｜ 字节 ★★ ｜ 阿里 ★★★ ｜ 腾讯 ★★★（微信系稳定性必问）**
> **追问链**：锁阻塞和 IO 阻塞在栈上怎么区分

**答案：** jstack 看状态：`BLOCKED`（争 synchronized）、`waiting on object monitor`（wait）、`parking`（AQS）；顺栈找锁持有者。
另一类是 **IO 阻塞**：栈卡在 socketRead/read，不是锁问题，要查下游（DB、RPC、网络）。

# 十一、虚拟线程（JDK21+）

## 11.1 M:N 模型、Carrier 载体线程、挂载/卸载
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★**
> **追问链**：虚拟线程栈存在哪 → 为什么能百万级
> **风格**：**趋势向上**，字节内部在调研；阿里云/中间件团队深挖

**答案：** 不是 OS 线程，由 JVM 调度；大量虚拟线程挂载在少量载体平台线程上；遇到 IO/park 时 JVM 保存执行栈并卸载虚拟线程，载体线程去跑别的；不阻塞 OS 线程，故可支撑百万级。栈为分段结构、动态伸缩。

## 11.2 pin 问题、synchronized 限制、适用场景
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★**
> **追问链**：哪些操作会 pin → 怎么规避

**答案：** 虚拟线程在 synchronized 块内阻塞时 JVM 无法卸载，会 pin 住载体线程使其跟着阻塞，失去优势；应改用 ReentrantLock。native 阻塞、部分 JNI 也会 pin。适合大量 IO 密集，不适合长 CPU 计算。

## 11.3 能否直接替换所有线程池？
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★ ｜ 腾讯 ★**
> 属场景判断题，答"不能无脑替换"并给出理由即可

**答案：** 不能。CPU 密集任务没收益；依赖 pin 的同步代码会退化；ThreadLocal 大对象在百万线程下会爆内存；且失去线程池的限流与背压能力（虚拟线程应配信号量限流）。

# 十二、手写 / 场景题

## 12.1 两线程交替打印 1~100
> **🟧 A ｜ 字节 ★★★（现场手写） ｜ 阿里 ★★ ｜ 腾讯 ★**
> **追问链**：用 wait/notify 还是 park → 为什么容易卡死

**答案思路：** 共享 volatile 标记 + LockSupport：打印完先 `unpark(对方)` 再 `park(自己)`。**必须先唤醒再 park**，否则双方都 park 会永久挂起。

## 12.2 生产者消费者（Condition）
> **🟧 A ｜ 字节 ★★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**

**答案思路：** 一把 Lock + 两个 Condition（notFull / notEmpty）；生产/消费都用 `while` 判条件；放/取后 signal 对侧队列。

## 12.3 DCL 单例 + volatile 解释
> **🟥 S ｜ 字节 ★★★ ｜ 阿里 ★★★（招牌） ｜ 腾讯 ★★★**

**答案：** 见 3.4。要点：双检 + volatile；解释 new 三步重排导致半初始化对象可见。

## 12.4 批量任务全部完成再回调
> **🟨 B ｜ 字节 ★★ ｜ 阿里 ★★ ｜ 腾讯 ★★**

**答案：** `CompletableFuture.allOf(...).join()` 或 CountDownLatch；注意 allOf 不传播异常，需逐个 handle。
