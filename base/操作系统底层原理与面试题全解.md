### 0.3 三问框架（遇到任何新机制先套这三问）

| 三问 | 含义 | 典型对照 |
|---|---|---|
| **虚拟化** | 把一份物理资源"变"成多份，或把有限变无限 | 虚拟内存 / 时间片 / 虚拟文件系统 / 虚拟网卡 |
| **隔离** | A 进程崩了不能影响 B；A 读不到 B 的数据 | 地址空间隔离 / 特权级 / namespace / cgroup |
| **并发正确性** | 多核 + 抢占下，共享数据不能错 | 锁 / 原子指令 / 内存屏障 / RCU |

**记忆锚点**：CPU 靠"**时分复用**"虚拟化，内存靠"**空分复用 + 按需分页**"虚拟化，磁盘靠"**文件抽象**"虚拟化。这三种虚拟化手段，就是操作系统的全部魔法。

## 第 1 章 操作系统的本质

### 1.1 一句话结论

> 操作系统是**硬件之上的第一个软件**，它把丑陋、稀缺、共享的硬件资源，包装成**统一、充足、私有**的抽象，并负责在多个使用者之间**安全地分配**这些资源。

### 1.2 四个目标（面试常考"操作系统的作用"）

| 目标 | 解释 | 具体手段 |
|---|---|---|
| **抽象 Abstraction** | 隐藏硬件细节，提供统一接口 | 进程抽象 CPU、虚拟地址抽象内存、文件抽象磁盘、socket 抽象网卡 |
| **资源管理 Multiplexing** | 多道程序共享有限硬件 | 调度器分配 CPU、页框分配器分配内存、块层分配磁盘带宽 |
| **隔离保护 Protection** | 一个程序不能伤害另一个 | 用户态/内核态、页表 U/S 位、TLB、能力（capability） |
| **持久化 Persistence** | 断电后数据还在 | 文件系统 + 块设备 + 日志/WAL |

### 1.3 内核架构：宏内核 vs 微内核 vs 混合

```
 宏内核 (Linux)                 微内核 (seL4 / QNX / Fuchsia)
┌──────────────────────┐      ┌───────────────────────────┐
│ 调度 内存 FS 网络 驱动 │      │ 微内核: 只做 地址空间/线程/IPC/调度│
│ 全部在同一地址空间     │      │ ┌────┐ ┌────┐ ┌────┐       │
│  互相直接函数调用      │      │ │FS  │ │NET │ │驱动│ 用户态 │
└──────────────────────┘      │ └────┘ └────┘ └────┘       │
  优点: 性能高、共享缓存      │  优点: 隔离好、可形式化验证 │
  缺点: 一个驱动崩全崩        │  缺点: IPC 开销大          │
                              └───────────────────────────┘
 混合内核 (Windows NT / macOS XNU): 微内核骨架 + 宏内核身段
```

| 维度 | 宏内核 | 微内核 |
|---|---|---|
| 性能 | 高（同一地址空间，函数调用） | 低（跨地址空间 IPC，上下文切换多） |
| 稳定性 | 差（驱动在核内） | 好（驱动崩了重启服务即可） |
| 可维护性 | 复杂 | 模块清晰 |
| 代表 | Linux、FreeBSD | QNX（车载）、seL4（形式化验证）、Fuchsia |

**延伸**：Linux 用**内核模块（LKM）** 部分弥补宏内核的缺点——模块可以动态加载卸载，但仍在 Ring 0、仍共享内核地址空间，所以"模块崩了系统照样 panic"。这就是为什么 eBPF 会被发明：它让内核里能跑"受验证器约束的、安全的小程序"，而不用加载一个不信任的模块。

| 目录 | 内容 | 对应面试题 |

## 第 2 章 用户态与内核态

### 2.1 一句话结论

> "用户态/内核态"不是两种软件，而是 **CPU 的两种特权级执行模式**；系统调用不是函数调用，而是一次**受控的、代价高昂的"越权申请"**。

### 2.2 特权级机制（x86 的 Ring 0～3）

| 环 | 谁在跑 | 能干什么 |
|---|---|---|
| Ring 0 | 内核 | 所有指令、所有内存、直接访问设备端口、改页表基址寄存器 CR3 |
| Ring 1/2 | 极少用（部分虚拟化/驱动） | — |
| Ring 3 | 用户程序 | 只能访问自己页表里 U/S=1 的页，执行**非特权指令** |

**关键点**：CPU 判断"你能不能执行某条指令 / 访问某个地址"，靠的是三个东西：
1. **CS 段寄存器的 CPL**（当前特权级）；
2. **页表项的 U/S 位**（该页是否允许 Ring 3 访问）；
3. **IDT 门描述符的 DPL**（该中断/异常门允许哪个特权级触发）。

**为什么这很重要**：`mov cr3, rax`（改页表）、`cli`（关中断）、`in/out`（访问端口）这些指令在 Ring 3 执行会直接 `#GP` 异常。所以用户程序想干这些事，唯一合法通道就是**系统调用**。

### 2.3 系统调用的完整路径（x86-64）

```
用户态                                                          内核态
────────────────────────────────────────────────────────────────────────────
 glibc: syscall(SYS_read, fd, buf, n)
   │ 把系统调用号(rax) + 参数(rdi,rsi,rdx,r10,r8,r9) 放寄存器
   ▼
 syscall 指令  ──────────────────► CPU: CPL 3→0，切到内核栈(从 TSS/percpu 取 rsp0)
                                   │
                                   ▼
                          entry_SYSCALL_64 (arch/x86/entry/entry_64.S)
                           1. swapgs：切 GS 基址（用户 TLS ↔ 内核 percpu）
                           2. 保存用户寄存器到内核栈，构造 pt_regs
                           3. 检查 syscall 号越界、seccomp 过滤
                           4. 查 sys_call_table 跳转 → __x64_sys_read
                                   │
                                   ▼
                          do_syscall_64 → 具体实现（如 vfs_read）
                                   │
                           返回值写入 pt_regs->ax
                                   │
                                   ▼
                          sysretq：恢复寄存器，CPL 0→3，回到用户态
```

**细节（面试加分项）**：

| 问题 | 答案 |
|---|---|
| 32 位怎么进内核？ | 早期 `int 0x80`（走 IDT 门，最慢）；后来 `sysenter/sysenter_return`（快速系统调用，用 MSR 存入口和栈） |
| x86-64 用哪些 MSR？ | `IA32_STAR`(0xC0000081)：存内核/用户 CS 段选择子；`IA32_LSTAR`(0xC0000082)：存 `entry_SYSCALL_64` 地址；`IA32_FMASK`(0xC0000084)：存要屏蔽的 EFLAGS 位 |
| 参数为什么用 `r10` 而不是 `rcx`？ | 因为 `syscall` 指令会用 `rcx` 保存返回地址、用 `r11` 保存 EFLAGS，`rcx` 被硬件占用了 |
| 返回值和错误怎么区分？ | 返回值 > -4096 视为错误码（`-EINVAL` 等），glibc 转成 `errno` |
| 系统调用号在哪查？ | `arch/x86/entry/syscalls/syscall_64.tbl`；`read=0, write=1, open=2, close=3, mmap=9, clone=56, execve=59, exit=60, futex=202, epoll_create=213, io_uring_setup=425` |
| 为什么 `syscall` 比 `int 0x80` 快？ | 不查 IDT（省一次内存访问）、不做段描述符特权级检查、`sysret` 直接按 MSR 恢复 CS/SS，路径短、分支少 |
| 一次系统调用多贵？ | 裸 `syscall+sysret` 约 **50～150ns**；叠加 KPTI（Meltdown 缓解，需切页表）后常见 **数百 ns 到 1μs**；真正的成本还有：TLB/分支预测器被污染、cache 冷启动 |

### 2.4 vDSO：不进内核也能"系统调用"

**问题**：`gettimeofday()`、`clock_gettime()`、`time()` 被程序调用得极其频繁（日志、超时判断），每次都进内核太亏。

**方案**：内核在启动时把一小段代码（`vvar` 页 + `vdso` 页）**映射到每个进程的地址空间**，其中包含当前时间、时钟精度等数据。glibc 直接读这块共享内存、在用户态算完返回。

```
进程地址空间
┌─────────────┐
│ 用户栈       │
├─────────────┤
│ mmap 区      │  ← [vvar]（内核只读数据：时间、seq 计数）
│  ...        │  ← [vdso]（代码：__vdso_gettimeofday）
└─────────────┘
```

**代价与坑**：内核更新时间时用 **seqlock**（版本号奇偶校验），vDSO 读到版本号变化要重读。所以它是"无锁读、极少重试"的经典案例——第 8 章 seqlock 会再讲。

### 2.5 切换的本质开销（第 3 章会复用）

一次用户态 ↔ 内核态切换，硬件/软件层面发生了什么：

| 层面 | 发生了什么 | 影响 |
|---|---|---|
| 特权级 | CPL 3→0→3 | 少量周期 |
| 栈 | 用户栈 → 内核栈（`TSS.rsp0` / `entry stack`） | 缓存污染 |
| 寄存器 | 保存/恢复 `pt_regs`（16 个通用寄存器 + 段 + EFLAGS） | 几十条指令 |
| 地址空间 | 普通系统调用**不切 CR3**（内核页表同时映射用户页）；KPTI 开启后要切 | TLB 部分失效 |
| 微架构 | 分支预测器、iTLB、uop cache 状态改变 | 间接开销可达直接开销的数倍 |

> **一句话**："系统调用便宜是因为它不切换地址空间、不切换线程；它贵是因为它污染 CPU 的预测状态，并且把'内核代码'塞进了你的 cache。"

## 第 3 章 进程与线程

### 3.1 一句话结论

> **进程 = 资源容器（地址空间 + 文件表 + 信号处理 + 凭证）**；**线程 = 调度实体（一组寄存器 + 栈）**。Linux 根本不为它们建两套机制——两者都是 `task_struct`，差别只在于 `clone()` 时**共享了哪些资源**。

### 3.2 从抽象到数据结构：PCB 与 task_struct

```
进程控制块 PCB (Linux 里叫 task_struct，约 3～9KB，含大量配置相关字段)
┌───────────────────────────────────────────────────────────┐
│ ① 标识      pid, tgid, comm[16], parent, children, sibling │
│ ② 状态      __state, exit_state, exit_code                │
│ ③ 调度      prio, static_prio, normal_prio, rt_priority    │
│             sched_entity(含 vruntime), policy, cpus_allowed│
│ ④ 内存      mm(mm_struct*), active_mm, vmacache            │
│ ⑤ 文件      files(files_struct*), fs(fs_struct*)           │
│ ⑥ 信号      pending, blocked, signal, sighand              │
│ ⑦ 内核栈    stack（x86-64 默认 16KB，THREAD_SIZE）           │
│ ⑧ 上下文    thread(thread_struct)：保存 rsp、callee-saved、  │
│             fs_base、gs_base、CR3 相关、FPU 状态             │
│ ⑨ 隔离/限额 nsproxy(namespace), cgroups, cred              │
└───────────────────────────────────────────────────────────┘
```

**注意 `mm` 与 `active_mm` 的区别**（高频细节题）：
- 普通进程 `mm == active_mm`；
- **内核线程**（kthreadd、kswapd、kworker）没有自己的用户地址空间，`mm = NULL`，它"借用"上一个被调度进来的进程的 `active_mm`（这叫 **lazy TLB**），避免每次进内核线程都切 CR3。

**内核栈为什么只有 16KB？**
1. 进程数多时，栈是纯开销（1000 个进程 = 16MB）；
2. 更重要的原因：**小栈能逼迫内核代码避免深递归**。VFS 路径解析、文件系统操作都被设计成循环/迭代，而不是递归。历史上曾用 8KB（32 位 4KB 页 × 2），x86-64 扩到 16KB。开启 `CONFIG_VMAP_STACK` 后内核栈是 vmalloc 区里带 guard page 的独立映射，栈溢出会立刻触发缺页而不是静默踩坏相邻内存。

### 3.3 进程状态机（必背图）

```
                     fork/clone
                          │
                          ▼
                   ┌─────────────┐  调度器选中   ┌─────────────┐
              ┌───►│ TASK_RUNNING│─────────────►│  运行在 CPU  │
              │    │ (就绪/运行)  │◄─────────────│             │
              │    └──────┬──────┘  时间片用完/   └─────────────┘
              │           │        被抢占
              │           │ 等待事件（read 阻塞、wait、sleep、futex）
              │           ▼
              │    ┌──────────────────────┐   事件到达（数据到、信号、锁释放）
              └────┤ TASK_INTERRUPTIBLE   │◄──────────────┐
                   │ (可被信号唤醒, S)     │               │
                   ├──────────────────────┤               │
                   │ TASK_UNINTERRUPTIBLE │               │
                   │ (D 状态: 不响应信号,  │───────────────┘
                   │  真正不可杀)          │   wake_up()
                   ├──────────────────────┤
                   │ TASK_KILLABLE (D+可杀)│
                   └──────────────────────┘
                          │ exit()  /  return from main
                          ▼
                   ┌─────────────┐  父进程 wait() 收尸   ┌─────────────┐
                   │EXIT_ZOMBIE  │─────────────────────►│ EXIT_DEAD   │
                   │(僵尸: 只剩PCB)│                     │(彻底释放)    │
                   └─────────────┘                     └─────────────┘
```

| 状态 | 标志 | 是否占 CPU | 能否被信号杀掉 | 典型场景 |
|---|---|---|---|---|
| Running | R | 是/就绪 | 是 | 正常执行 |
| Interruptible | S | 否 | **是**（`kill -9` 有效） | `read` 等 IO、`sleep`、`accept` |
| Uninterruptible | D | 否 | **否**（`kill -9` 无效！） | 磁盘 IO 等待、NFS 无响应、驱动 bug |
| Zombie | Z | 否 | 已死，无法杀 | 父进程没 `wait` |
| Stopped | T | 否 | 是 | `SIGSTOP`、调试断点 |

**面试陷阱**：`kill -9` 杀不掉 D 状态进程。正确做法是等 IO 回来，或者重启（或 `reboot` 都卡住时只能硬断电）。D 状态大量堆积 = 存储/驱动故障或 NFS 挂死，这是运维经典事故。

### 3.4 fork 的完整过程（源码级）

```
sys_fork → _do_fork(SIGCHLD, 0, 0, NULL, NULL, 0)
   │
   ├─ copy_process()
   │    ├─ dup_task_struct()      复制 task_struct + 分配新内核栈
   │    ├─ copy_semundo/copy_files/copy_fs/copy_sighand  按 flags 决定复制还是共享
   │    ├─ copy_mm()             → dup_mm()：复制 mm_struct、VMA、**复制页表**
   │    │                          关键：父子所有私有可写页的 PTE 都改成**只读**，R/O + refcount++
   │    ├─ copy_thread()         → 设置子进程内核栈里的 pt_regs，令其"看起来像刚被 syscall 返回"，
   │    │                          且返回值为 0（这就是 fork 返回两次的实现原理！）
   │    ├─ alloc_pid()           分配新 pid
   │    └─ sched_fork()          设置调度参数，子进程先不立刻跑（唤醒在最后）
   │
   └─ wake_up_new_task()         把子进程挂到 runqueue
```

**"fork 为什么返回两次，一次返回 0 一次返回 pid？"**

不是真的返回两次，而是：父进程执行完 `copy_thread` 后**从系统调用正常返回**（返回值 = 子 pid）；子进程的内核栈是**被构造出来的**，`pt_regs->ax` 被置 0，调度器一旦选中它，它就沿"从 syscall 返回"的路径回到用户态，于是看到返回值 0。**同一段用户态代码、两个不同的栈、两个不同的返回寄存器值**。

**COW 的完整链路**：

```
fork 后:  PTE 全部只读，physical page refcount = 2
   │
   ├─ 父/子任一写这块内存
   │      ▼
   │  CPU 触发 #PF（page fault，因为 PTE 是只读但 VMA 是可写）
   │      ▼
   │  do_page_fault → handle_mm_fault → do_wp_page()
   │      ├─ 若 page->_refcount == 1（另一个进程已退出）→ 直接恢复可写，零拷贝！
   │      └─ 否则 alloc_pages 新页 → copy_page 拷贝内容 → 改 PTE 指向新页且可写 → 旧页 refcount--
   ▼
 这就是 copy-on-write：写时才复制，读永不复制
```

**延伸：`fork` 的性能问题与优化**
1. **`vfork`**：子进程共享父进程地址空间（`CLONE_VM`），父进程阻塞直到子进程 `exec/exit`。目的是省掉页表复制，但极其危险（子进程改栈会踩坏父进程）。
2. **`posix_spawn`**：内部用 `vfork` + `execve`，glibc 现代化实现，比 `fork+exec` 快得多。
3. **COW 的隐性成本**：`fork` 本身很快（不拷数据），但之后大量写操作会引发大量缺页——Redis 的 `bgsave` 就是典型例子（COW 期间内存可能翻倍、延迟抖动）。这也解释了为什么大内存进程 `fork` 要谨慎，以及为什么 Redis 用 `fork` 做 RDB 快照会"内存膨胀"。

### 3.5 execve：换掉整个"人格"

```
execve("/bin/ls", argv, envp)
   │
   ├─ 打开文件、识别格式（ELF / 脚本 shebang）
   ├─ 权限检查（x 位、setuid）
   ├─ 解析 ELF：读 program header，建立新的 mm_struct，映射 text/data/bss/heap/stack
   │     （text 是文件私有映射 → 多进程可共享同一份物理页！这就是"可执行文件只有一份物理内存"的原因）
   ├─ exec_mmap()  ← **切换地址空间**（旧 mm 引用计数--，可能释放）
   ├─ 保留 fd 表（除 FD_CLOEXEC 的），重置信号处理函数为默认（被忽略的 SIG_IGN 保留）
   ├─ 把 argv/envp/auxv 复制到新用户栈顶
   └─ 返回到 ELF 入口 e_entry（通常是 _start → __libc_start_main → main）
```

**关键点**：`execve` **成功不返回**（返回即失败）。所以 `fork+exec` 组合中，子进程的那次 `fork` 返回 0 后立刻被新程序覆盖。

**ELF 加载与页表共享的联动**（面试延伸）：同一个可执行文件被 100 个进程运行时，`text` 段（代码）的物理页只有一份，各进程页表指向同一物理页（只读，`page_mapcount=100`）。这就是"进程隔离但代码共享"的实现。反之，堆、栈、数据段是私有匿名页，各进程独立。

### 3.6 exit 与僵尸/孤儿

```
exit() → do_exit()
   ├─ exit_mm()      释放 mm（如果是线程组最后一个使用者）
   ├─ exit_files/exit_fs/exit_sem
   ├─ exit_notify()  给父进程发 SIGCHLD、把子进程过继给 init/subreaper
   ├─ 设置 exit_state = EXIT_ZOMBIE
   └─ schedule()     **永不返回**：这行代码之后就是死代码
```

| 概念 | 定义 | 危害 | 处理 |
|---|---|---|---|
| **僵尸进程** | 子进程已死，但父进程未 `wait`，PCB 未释放 | 占 pid 和少量内核内存；大量会耗尽 pid | 父进程 `wait/waitpid`；或 `signal(SIGCHLD, SIG_IGN)` 让内核自动回收 |
| **孤儿进程** | 父进程先死，子进程被 `init(1)`/`subreaper` 收养 | 无危害 | 自动被收养并最终回收 |
| **僵尸不可杀** | `kill -9 僵尸pid` 无效 | — | 只能杀它的父进程，让 init 收尸 |

**`PR_SET_CHILD_SUBREAPER`**：让某个进程成为"次级收割者"，容器里 systemd 或 tini 干这事——否则容器 pid 1 退出后，孙进程变孤儿被宿主的 init 收养，容器的 namespace 里可能出现奇怪的现象。**这是容器里"必须有个 init 进程"的根本原因**。

### 3.7 Linux 的线程模型：clone 的参数决定一切

| 资源 | 相关标志 | 进程（fork） | 线程（pthread_create） |
|---|---|---|---|
| 地址空间 `mm` | `CLONE_VM` | 复制 | **共享** |
| 文件表 `files` | `CLONE_FILES` | 复制 | **共享**（所以 `close` 会影响同进程其他线程） |
| 文件系统信息 `fs`（cwd/umask） | `CLONE_FS` | 复制 | **共享** |
| 信号处理 `sighand` | `CLONE_SIGHAND` | 复制 | **共享** |
| 信号屏蔽字/待处理信号 | `CLONE_THREAD` | 独立 | **共享**（线程组内共享） |
| 线程组（tgid 相同） | `CLONE_THREAD` | 否 | **是** |
| TLS（FS 段基址） | `CLONE_SETTLS` | 新 | 每线程独立（`arch_prctl(ARCH_SET_FS)`） |
| 命名空间 | `CLONE_NEW*` | 继承 | 继承 |

```
pthread_create 实际等价于：
  clone(CLONE_VM | CLONE_FS | CLONE_FILES | CLONE_SIGHAND |
        CLONE_THREAD | CLONE_SYSVSEM | CLONE_SETTLS |
        CLONE_PARENT_SETTID | CLONE_CHILD_CLEARTID, ...)

CLONE_THREAD   → 共享 tgid（ps 里显示为同一进程），信号按线程组处理
CLONE_SETTLS   → 设置新线程的 FS 基址，指向它自己的 TCB（线程控制块）
CLONE_CHILD_CLEARTID → 线程退出时内核清零 futex 变量，pthread_join 靠它实现
```

**这意味着**：`ps -eLf` 看到的 LWP（轻量级进程）就是内核眼里的线程；`/proc/<pid>/task/<tid>/` 就是每个线程的信息。**Linux 不区分"进程调度"和"线程调度"——调度器眼里只有 task。**

**线程共享 vs 私有总结**（必背）：

| 共享 | 私有 |
|---|---|
| 代码段、数据段、堆、全局变量、打开的文件、信号处理、cwd | 栈、寄存器、TLS、errno（实际是 TLS 变量）、信号屏蔽字（POSIX 语义上每线程独立，Linux 实现上由 CLONE_THREAD 共享进程级 pending）、线程 ID |

### 3.8 上下文切换：真正发生了什么

```
schedule() 选中 next
   │
   ├─ context_switch(prev, next)
   │    ├─ switch_mm(prev->active_mm, next->mm)  → 若 mm 不同则 load_cr3()
   │    │      （同进程内切线程：mm 相同，**不切 CR3，TLB 不用刷**——线程切换比进程切换便宜的核心原因）
   │    └─ switch_to(prev, next)
   │          __switch_to_asm:
   │            push rbp/rbx/r12-r15   ← 保存 callee-saved 到 prev 的内核栈
   │            mov [prev->thread.sp], rsp   ← 保存栈指针
   │            mov rsp, [next->thread.sp]   ← 切到 next 的内核栈
   │            ... 恢复 next 的 callee-saved
   │            （可选：切 FS/GS 基址、FPU 状态）
   │            ret                          ← 返回到 next 上次"躺下"的地方
   ▼
 next 从它上次被切走的位置继续执行（可能是刚返回用户态，也可能是继续内核代码）
```

**成本量化（面试常考"切换开销多大"）**：

| 成本项 | 量级 | 说明 |
|---|---|---|
| 直接成本 | **1～3 μs**（有时 0.5μs 起） | 保存/恢复寄存器、切栈、更新 TSS.rsp0、调度器开销 |
| TLB | 进程切换要刷（或用 PCID 打标签避免全局刷） | 之后每次访存都可能 page walk，**几十到几百 ns/次** |
| Cache | 新任务代码/数据不在 L1/L2 | 冷启动，可能持续数万周期 |
| 分支预测器 | BTB/RAS 记录的是旧任务的路径 | 大量 mispredict |
| 实际经验值 | **2～10 μs**（含间接） | 所以"每秒切换百万次"是灾难；`vmstat` 的 `cs` 列可观测 |

**延伸：为什么"线程切换比进程切换快"这个说法要打折扣？**
- 同进程线程切换：**不换页表（不刷 TLB）、不换文件表**，寄存器+栈切换，快；
- 但**cache 污染照样存在**（不同线程访问不同数据）；
- 跨进程切换：CR3 变化 + TLB 失效（现代 CPU 用 **PCID** 给 TLB 项打 ASID 标签，可以避免全局刷新，只失效自己的项）；
- 所以更准确的说法是：**线程切换省掉的是"地址空间切换"这一块**，其他开销依旧。

### 3.9 协程与用户态调度

**为什么需要协程**：一个线程 8MB 栈（虚拟）+ 内核栈 16KB + 切换微秒级；10 万并发连接用线程模型直接爆炸。协程把"切换"降到**用户态寄存器保存 + 栈切换（几十 ns）**，且栈可以很小（Go 初始 2KB，可增长）。

| 模型 | 映射 | 代表 | 优点 | 缺点 |
|---|---|---|---|---|
| **1:1** | 1 用户线程 : 1 内核线程 | Linux NPTL、Java 平台线程 | 简单、能用多核、阻塞调用天然可用 | 创建/切换贵，数量受限 |
| **N:1** | N 协程 : 1 内核线程 | 早期 Java 绿线程、Python gevent | 极轻量 | 无法利用多核，一个阻塞全阻塞 |
| **M:N** | M 协程 : N 内核线程 | Go、Erlang | 兼顾轻量与多核 | 调度器复杂（需要处理系统调用阻塞、抢占） |

**Go 调度器 GMP 速览**（面试常问"协程为什么快"）：

```
G (goroutine, 2KB 初始栈)
M (machine = OS thread)
P (processor = 逻辑 CPU, 数量 = GOMAXPROCS)
         ┌───────┐   ┌───────┐
         │  P0   │   │  P1   │   每个 P 有本地 runq(256)
         │ runq  │   │ runq  │   全局 runq 兜底
         └───┬───┘   └───┬───┘
             │           │
        ┌────▼───┐  ┌────▼───┐
        │   M0   │  │   M1   │
        └────────┘  └────────┘
关键机制：
  1. work stealing：P 本地队列空了，去别的 P 偷一半
  2. handoff：G 陷入系统调用阻塞时，M 与 P 解绑，P 交给别的 M 继续跑
  3. netpoll：网络 IO 用 epoll，就绪的 G 被重新塞回 runq
  4. sysmon：后台线程，发现 G 运行超 10ms 发起**抢占**（Go 1.14+ 用信号 SIGURG 做异步抢占）
  5. 栈增长：栈溢出时拷贝到 2 倍大的新栈，指针需修正（所以 Go 的指针不是 C 的裸指针）
```

**有栈 vs 无栈协程**：

| 类型 | 栈 | 代表 | 特点 |
|---|---|---|---|
| 有栈（stackful） | 每个协程独立栈 | Go、Lua coroutine | 可以在任意函数深处 yield |
| 无栈（stackless） | 状态机，无独立栈 | Rust async/await、C++20 coroutine、JS async | 零栈开销，但只能在 await 点挂起，代码被编译器改写成状态机 |

## 第 4 章 CPU 调度

### 4.1 一句话结论

> 调度器是"分蛋糕的人"：在**吞吐、延迟、公平、实时性**四个互相冲突的目标之间做取舍，Linux 的答案是——**用权重（nice）定义比例，用虚拟运行时间（vruntime）保证公平**。

### 4.2 调度目标与策略分类

| 场景 | 目标 | 算法 | 例子 |
|---|---|---|---|
| 批处理 | 吞吐量、周转时间 | FCFS、SJF、HRRN | 大数据离线作业 |
| 交互式 | **响应时间**、公平 | 时间片轮转、优先级、MLFQ、CFS | 服务器、桌面 |
| 实时 | **确定性**、截止时间 | RM、EDF、FIFO/RR | 车载、工业控制 |

**核心权衡**：时间片短 → 响应好、切换多；时间片长 → 吞吐高、交互差。**抢占式 vs 协作式**：Linux 是抢占式（内核可抢占，`CONFIG_PREEMPT`），但也保留 `preempt_count` 保护临界区。

### 4.3 演进史（面试问"Linux 调度器怎么演化"）

```
O(n) 调度器（2.4）: 遍历所有任务选最优 → 任务多时 O(n)，且不区分交互/批处理
   │
O(1) 调度器（2.6 早期）: 每优先级一个队列（active + expired 双数组），位图找最高优先级 → O(1)
   │  问题：交互任务识别靠启发式（sleep_avg），不公平、抖动大
   ▼
CFS（2.6.23，2007，Ingo Molnar）: 完全公平，用 vruntime + 红黑树 → O(log n)
   │  问题：权重模型下延迟与公平的矛盾、"唤醒抢占"抖动
   ▼
EEVDF（6.6，2023，Peter Zijlstra）: 在 CFS 的权重公平之上引入"虚拟截止时间"，显式建模延迟
```

### 4.4 CFS 深入

**核心思想**：不设固定时间片，而是**按权重分配 CPU 时间比例**。理想状态下，n 个任务同时运行，每个应得到 `1/n` 的 CPU；nice 值不同则按权重比例分配。

**vruntime 的定义**：

```
vruntime += 实际运行时间 × (NICE_0_LOAD / 该任务权重)

nice = 0  → weight = 1024，系数 1.0
nice = -1 → weight ≈ 1277，系数 ≈ 0.80 （vruntime 增长慢 → 更容易被选中 → 优先级高）
nice = 1  → weight ≈ 820， 系数 ≈ 1.25
每差 1 个 nice，权重约差 1.25 倍；差 10 个 nice ≈ 10 倍 CPU 份额
```

**红黑树**：以 `vruntime` 为 key，**最左节点就是下一个要运行的任务**。每次调度取 `rb_leftmost`，O(1)；插入/删除 O(log n)。`min_vruntime` 单调递增，用于给新唤醒任务"补票"（新任务 `vruntime = max(自身, cfs_rq->min_vruntime - 补偿)`，防止刚醒来的任务因为 vruntime 太小而独占 CPU，也防止它被饿死）。

**时间片怎么算**：

```
sched_latency  = 6ms × (1 + ilog2(nr_running))     ← 目标延迟，随任务数增长但受上限约束
min_granularity = 0.75ms                            ← 单次运行下限，防止切换过频
sched_slice(任务) = sched_latency × (该任务权重 / 所有可运行任务权重和)
                   且不低于 min_granularity
```

**举例计算（面试真题爱考）**：3 个任务，nice 分别 0、0、5（权重 1024、1024、335），`nr_running=3` → `sched_latency = 6 × (1+ilog2(3)) = 6 × 2 = 12ms`，总权重 2383：
- nice 0 的任务各得 `12 × 1024/2383 ≈ 5.16ms`
- nice 5 的任务得 `12 × 335/2383 ≈ 1.69ms`

**唤醒抢占（wakeup preemption）**：任务被唤醒时，如果它的 `vruntime` 比当前任务的 `vruntime` 小超过 `wakeup_granularity`（默认 1ms 折算），就抢占当前任务。这是"交互任务（如键盘、网络回调）能立刻响应"的原因。

**组调度（group scheduling）**：如果不做组调度，用户 A 起 100 个线程、用户 B 起 1 个线程，B 只能拿到 1% CPU。CFS 用 `task_group` 形成层级树：**先按组分配 CPU 份额，组内再按任务分**。cgroup 的 `cpu.weight` 就是挂到这棵树上。**这是容器 CPU 限额（`cpu.max` 的 quota/period）能工作的基础**。

### 4.5 EEVDF（6.6+）为什么替代 CFS

CFS 的问题：它只有"权重公平"，不能表达"**我要求在多长时间内被调度一次**"。用 nice 调低优先级会让延迟变差，用 nice 调高又会抢别人的份额——**公平性和延迟耦合在一起**。

EEVDF（Earliest Eligible Virtual Deadline First）：
1. 每个任务有 **lag**（应得时间 - 已得时间）；`lag > 0` 才算 **eligible（有资格）**；
2. 在 eligible 的任务里，选 **virtual deadline 最早**的：`vd = vruntime + slice/weight`；
3. 请求短时间片的任务（`sched_setattr` 设 slice）自然获得更低延迟，而不用改 nice。

**一句话**：**CFS 只管"分多少"，EEVDF 还能管"多久给一次"**。面试里能说到这一层，属于"读过 6.x 内核"的加分项。

### 4.6 实时调度

| 策略 | 说明 | 优先级 |
|---|---|---|
| `SCHED_FIFO` | 先进先出，同优先级先来先跑，**不 time-slice**，除非被更高优先级抢占或主动让出 | 1～99（数字大优先） |
| `SCHED_RR` | FIFO + 时间片轮转（同优先级之间） | 1～99 |
| `SCHED_DEADLINE` | CBS/EDF：给定 runtime/deadline/period，内核保证带宽 | 高于所有 RT |
| `SCHED_NORMAL/BATCH/IDLE` | CFS 类 | nice -20～19 |

**RT throttling**：`/proc/sys/kernel/sched_rt_runtime_us = 950000`（每 1s 周期内 RT 最多跑 950ms）。**为什么需要**：如果 RT 任务写死循环，普通任务永远拿不到 CPU，系统"假死"，连 shell 都进不去。这 5% 是留给 CFS 的"逃生通道"。

**优先级反转**（经典必考）：
```
低优先级 L 持有锁 → 高优先级 H 要这把锁，被阻塞 → 中优先级 M 抢占 L
结果：H 等 M（M 和 H 无关！）
解决：① 优先级继承（PI）：L 临时提升到 H 的优先级，快速跑完释放锁
      ② 优先级天花板：锁被获取时，持有者提升到该锁可能被使用的最高优先级
      ③ 禁止中断/关抢占减少临界区
Linux: rt_mutex 实现 PI；futex 有 PI futex（FUTEX_LOCK_PI）
历史案例: 1997 年火星探路者号因优先级反转反复重启
```

### 4.7 多核调度与负载均衡

```
            ┌─────────┐
            │ CPU0 rq │──┐
            └─────────┘  │   sched_domain 层次（从下到上）：
            ┌─────────┐  │   SMT(超线程) → MC(同 socket 核) → NUMA(节点) → 全系统
            │ CPU1 rq │──┼──►  periodically: load_balance() 拉取/推走任务
            └─────────┘  │   触发时机: 时钟 tick、新任务唤醒、CPU 变 idle、exec
            ┌─────────┐  │
            │ CPU2 rq │──┘
            └─────────┘
关键概念：
  · 负载 ≠ 任务数：用"权重 + 利用率"综合衡量（PELT：per-entity load tracking，指数衰减）
  · 迁移成本：cache 亲和性（尽量不跨核迁移）、NUMA（跨节点访存延迟高）
  · 唤醒亲和：wake_affine 优先选"唤醒者所在的核"或"共享 cache 的核"
  · cpuset / sched_setaffinity 可人为绑核（DPDK、实时业务常用）
  · NOHZ / NOHZ_FULL：空闲核停掉 tick，减少唤醒（对延迟敏感业务可配 isolcpus）
```

**常见追问**：`load average` 到底是什么？
它**不是 CPU 使用率**！它是"**运行队列长度（R）+ 不可中断睡眠任务数（D）**"的指数滑动平均（1/5/15 分钟）。所以 load 很高但 CPU 很低 → 大量 D 状态（IO 卡住）；这是排查"负载高但 CPU 闲"的第一判断依据。Linux 的 load 计算包含 D 状态，这是与 Unix 的重要差异。

## 第 5 章 虚拟内存与地址翻译

### 5.1 一句话结论

> 虚拟内存是操作系统最重要的"骗术"：**给每个进程一份独立、连续、超大的地址空间**——实际上背后是一堆可能不连续、可能不在内存、甚至不存在（全零页）的物理页。

### 5.2 虚拟内存解决了什么（五大价值）

| 价值 | 解释 | 如果没有会怎样 |
|---|---|---|
| **隔离** | 进程 A 无法寻址进程 B 的内存（页表里没有那项） | 一个野指针写坏别的进程 |
| **抽象** | 每进程都有从 0 开始的连续空间，链接器不用考虑物理布局 | 程序必须感知物理地址、无法重定位 |
| **按需** | 用到才分配（demand paging），不必一次性加载 | 启动慢、内存浪费 |
| **共享** | 多个进程页表指向同一物理页（代码段、共享库、共享内存） | 内存成倍浪费 |
| **超额分配** | 虚拟总量 >> 物理内存（配合 swap、mmap、COW） | 无法运行大程序 |

### 5.3 地址翻译全过程（x86-64 四级页表）

```
 用户虚拟地址 VA (48 bit 有效)
 ┌──────┬──────┬──────┬──────┬──────┬────────────┐
 │ 无关 │ PML4 │ PDPT │  PD  │  PT  │  页内偏移   │  ← 高16位需符号扩展（规范地址）
 │      │ 9bit │ 9bit │ 9bit │ 9bit │   12bit    │
 └──────┴──┬───┴──┬───┴──┬───┴──┬───┴────────────┘
            │      │      │      │
            ▼      ▼      ▼      ▼
  CR3 ──► PML4 ──► PDPT ──► PD ──► PT ──► 物理页框 + offset = PA
        (512项)  (512项)  (512项)  (512项)
        每项 8 字节 → 每张页表 4KB
        9+9+9+9+12 = 48 bit  →  256TB 虚拟空间/进程
```

**页表项（PTE）关键标志位**：

| 位 | 名称 | 含义 |
|---|---|---|
| 0 | P (Present) | 1=在内存；0=不在（缺页） |
| 1 | R/W | 1=可写；0=只读（COW 靠它） |
| 2 | U/S | 1=用户可访问；0=仅内核（隔离靠它） |
| 5 | A (Accessed) | 硬件置 1，供 LRU/页回收参考 |
| 6 | D (Dirty) | 硬件置 1，表示被写过，回写磁盘时用 |
| 7 | PS | 1=大页（2MB/1GB），此层即终止遍历 |
| 63 | NX | 不可执行（防代码注入） |
| 51:12 | 物理页框号 | 目标物理地址高位 |

**页表带来的两个问题及解法**：

| 问题 | 表现 | 解法 |
|---|---|---|
| **空间爆炸** | 32 位 4KB 页 + 单级页表 = 进程 4MB 页表；64 位单级更是天文数字 | **多级页表**：只给用到的区域建表，稀疏空间不再浪费 |
| **访存次数** | 四级页表 = 1 次数据访问 + 4 次页表访问 = 5 次访存，慢 5 倍 | **TLB**（MMU 内的页表项缓存）+ 大页 |

### 5.4 TLB 深入

```
CPU 发 VA
   │
   ▼
┌──────────────┐  命中（L1 dTLB ~64 项, 1~2 cycle 找到 + 总延迟 ~10 cycle）
│     TLB      │──────────────► PA ──► L1/L2/L3/DRAM
│  L1: 分 iTLB/dTLB  │
│  L2: STLB (统一, ~1536 项, 4K/2M 共用) │
└──────┬───────┘
       │ 未命中
       ▼
  硬件 page walker 遍历 4 级页表（4 次访存，每次可能 L1 miss）
       │  若途中某级 P=0 → 缺页异常（#PF）
       ▼
  填充 TLB（受 PCID/ASID 标记），继续执行
```

**关键数据（面试可提）**：TLB 命中率哪怕下降 1%，性能都可能掉 5～10%（因为 page walk 是"访存放大 4 倍"并且**串行依赖**）。

**TLB 相关的经典问题**：

| 问题 | 说明 |
|---|---|
| 为什么切进程要刷 TLB？ | 不同进程 VA→PA 映射不同，必须失效。**PCID（ASID）** 给每条 TLB 项打进程标识，避免全局刷新，只失效自己的项 |
| TLB shootdown | 多核下，一个核改了页表（如 munmap），必须发 **IPI** 让其他核的 TLB 失效。这是多线程大量 mmap/munmap 的性能瓶颈（"TLB 弹幕"） |
| VIPT vs PIPT | 大多数 L1 cache 是 VIPT（虚拟索引物理标记），可并行做 TLB 查找和 cache 索引；同物理页若有多个虚拟地址别名（alias），需靠"页着色"或硬件保证一致 |
| 大页为什么好 | 2MB 页让一个 TLB 项覆盖 2MB（而非 4KB），TLB 有效覆盖范围扩大 512 倍，page walk 从 4 级降到 3 级（PS 位提前终止） |

**大页（HugePage）**：

| 类型 | 说明 | 优点 | 缺点 |
|---|---|---|---|
| 显式大页 `hugetlbfs` | 预留、`MAP_HUGETLB` 显式申请 | 稳定、不走 swap、可预留 | 需要预先分配、管理复杂 |
| 透明大页 THP | `khugepaged` 后台合并、`madvise(MADV_HUGEPAGE)` | 自动、零配置 | **内存放大**（一个 4KB 页也占 2MB）、**回收慢/分配时 compaction 造成延迟抖动**（Redis、JVM 常见坑） |
| 1GB 页 | 需显式申请 | 极大减少 TLB 压力 | 极少、碎片要求高 |

> **生产建议**：数据库/Redis 这类延迟敏感服务，通常 `echo never > /sys/kernel/mm/transparent_hugepage/enabled`，避免 THP 的 compaction 抖动。

### 5.5 缺页中断：虚拟内存的心脏

```
CPU 访问 VA → 页表项 P=0 → #PF (Page Fault)
   │
   ▼
do_page_fault(regs, error_code)     ← error_code 编码了：P(存在?)/W(写?)/U(用户?)/RSVD/I(取指?)
   │
   ├─ 地址在用户空间？ (addr < TASK_SIZE_MAX) 否则 → 内核态缺页（可能是 vmalloc 未建映射 / 内核 bug）
   │
   ├─ 查 VMA（用 maple tree）: 地址落在某个已注册的 vma 里吗？
   │     ├─ 否 → 非法访问 → **SIGSEGV**（段错误！）
   │     └─ 是 → 检查权限（写只读 VMA → SIGSEGV；栈越界接近 → 扩张栈 VMA）
   │
   ▼
handle_mm_fault → __handle_mm_fault
   │
   ├─ 页表缺失（PUD/PMD/PTE 未分配） → 逐级分配页表（这本身也可能要分配内存）
   │
   ▼
 分流（do_fault 的不同路径）：
   ┌──────────────────────────────────────────────────────────────┐
   │ ① 匿名页 + 读 → do_anonymous_page：分配 **zero page**（全局共享的全零物理页，只读）│
   │    写时再 COW 分配真实页 —— 这就是"新 malloc 的内存不占物理内存"的原理      │
   │ ② 文件页 → do_fault → filemap_fault：查 page cache                          │
   │     命中 → 直接映射（**minor fault，轻微缺页**）                            │
   │     未命中 → 发起磁盘读（**major fault，主要缺页**，几十 μs ～ ms）            │
   │ ③ 写时复制页 → do_wp_page → 复制或复用（见 3.4）                            │
   │ ④ 共享页 → do_shared_fault → 映射到 page cache（多进程共享同一物理页）        │
   └──────────────────────────────────────────────────────────────┘
   │
   ▼
 更新 PTE（写回硬件）、可能 flush TLB、retry 指令
```

**minor vs major fault（必背对比）**：

| 类型 | 触发条件 | 是否需要 IO | 典型耗时 | 观测 |
|---|---|---|---|---|
| **Minor（轻微）** | 页在内存（page cache 命中 / zero page / COW 复用） | 否 | **0.5～2 μs** | `minor` 计数 |
| **Major（主要）** | 页不在内存，需从磁盘/swap 读 | 是 | **几十 μs（SSD）～ ms（HDD）** | `majflt` 计数 |

`/usr/bin/time -v` 或 `/proc/<pid>/stat` 的 `minflt/majflt` 可直接观测。**"服务启动慢、CPU 不高、磁盘读很多" 常见原因就是大量 major fault + 预读不足。**

**延伸：为什么"申请内存不占物理内存"？**
`malloc(1GB)` → glibc 走 `mmap` → 内核只建 VMA，不建 PTE；第一次读 → zero page（共享，0 物理开销）；第一次写 → 分配真实页。所以"虚拟内存"和"RSS"是两个概念：

| 指标 | 含义 | 查看 |
|---|---|---|
| VSS / VSZ | 虚拟地址空间总量（含未映射、mmap 但未触碰） | `ps -o vsz` |
| RSS | 实际驻留物理内存（含共享页、page cache 中映射的部分） | `ps -o rss`、`/proc/pid/status` 的 VmRSS |
| PSS | 按共享比例折算的 RSS（多进程共享库不被重复计算） | `/proc/pid/smaps_rollup` |
| USS | 独占内存 | smaps 里 Private_* 求和 |

### 5.6 内核地址空间与 KPTI

```
x86-64 地址空间布局（48 位，用户/内核各占一半）
0x0000_0000_0000_0000 ┬─────────────────┐
                      │ 用户空间 (128TB)  │  进程私有：代码/堆/栈/mmap
0x0000_7FFF_FFFF_FFFF ┴─────────────────┘
0xFFFF_8000_0000_0000 ┬─────────────────┐
                      │ 内核直接映射区    │  physmap：物理内存全量映射（便于内核直接访问）
                      │ vmalloc 区        │  不连续的虚拟映射（大块、模块、vmalloc）
                      │ vmemmap           │  struct page 数组
                      │ 内核代码/数据      │
0xFFFF_FFFF_FFFF_FFFF ┴─────────────────┘
```

**KPTI（Kernel Page Table Isolation，4.15 引入）**：Meltdown 漏洞让用户态能"猜读"内核映射的内存，于是内核改成**两套页表**：用户态页表里内核部分只留极少的 trampoline 代码（进/出内核时切换 CR3）。代价是**每次系统调用/中断都要切页表**（用 PCID 缓解但不为零），某些场景系统调用开销增加 2～3 倍。**这是"为什么现在系统调用更贵了"的标准答案。**

## 第 6 章 物理内存管理

### 6.1 一句话结论

> 物理内存管理是一条**三级流水线**：`伙伴系统（管页框）` → `SLUB（管小对象）` → `page cache（管文件数据）`，外加一个 `回收器（kswapd/直接回收）` 兜底。

### 6.2 三级分配器全景

```
                        ┌──────────────────────────────────┐
   申请 8 字节 kmalloc   │  SLUB 分配器                      │
   ───────────────────► │  按 2 的幂/size class 建 kmem_cache │
                        │  每 CPU 一个 current slab（无锁快路径）│
                        └──────────────┬───────────────────┘
                                       │ slab 不够时向伙伴要整页(new_slab)
   申请 4KB 以上/整页      ┌────────────▼───────────────────┐
   alloc_pages(order) ──► │  伙伴系统 (Buddy)                │
                        │  free_area[order], order 0..10     │
                        │  分配：找不到就向上一级"借"并劈半    │
                        │  释放：相邻伙伴空闲则合并（coalesce） │
                        └──────────────┬───────────────────┘
                                       │ 物理页框 → 建页表
                                       ▼
                                ┌──────────────┐
                                │  struct page  │  每 4KB 物理页一个描述符（~64B）
                                │  vmemmap 数组  │  100GB 内存 = 26M 页 = 1.6GB 描述符
                                └──────────────┘
```

**为什么是"伙伴"而不是链表**：伙伴系统保证**合并可行**（只有 2^k 对齐的相邻块才互为伙伴），从而在反复分配/释放后仍能得到大块连续内存。代价是**外部碎片**（内存总量够但没有连续的大块）。

**per-CPU 页缓存（pcp）**：单页分配走 `per_cpu_pages`，无锁、极快，避免每次都抢 zone->lock。批量拿（如 64 页）再回填。

**SLUB 的关键设计**（面试爱问"slab 为什么快"）：
1. **对象复用**：`task_struct`、`dentry`、`inode` 都有专属 cache，分配时不用初始化/清零整块；
2. **per-CPU current slab**：绝大多数分配/释放**不加锁**；
3. **对象内嵌 freelist**：空闲对象本身存下一个空闲对象的指针，零额外元数据；
4. **NUMA 感知**：per-node cache，优先本地节点分配；
5. 对比 SLAB/SLUB/SLOB：SLUB 是当前默认（元数据最少、可调试性好）。

**kmalloc vs vmalloc vs kmap**：

| API | 特性 | 用途 |
|---|---|---|
| `kmalloc` | **物理连续**，直接映射区，快 | 大多数内核对象、DMA 缓冲（小块） |
| `vmalloc` | **虚拟连续、物理不连续**，需建页表，慢 | 大块、模块加载 |
| `__get_free_pages` | 直接拿 order 页 | 页表、大缓冲 |
| `dma_alloc_coherent` | 物理连续 + 一致性映射 | 设备 DMA |

### 6.3 内存 zone 与 NUMA

```
NUMA node 0                        NUMA node 1
┌───────────────────────┐          ┌───────────────────────┐
│ ZONE_DMA   (<16MB, 老设备)│       │  ...                 │
│ ZONE_DMA32 (<4GB, 32位设备)│      │                      │
│ ZONE_NORMAL (普通可映射)  │        │                      │
│ ZONE_MOVABLE(可迁移, 支持热插拔/大页)│ │                    │
└───────────────────────┘          └───────────────────────┘
     本地访问 ~80ns                      远端访问 ~150-300ns
```

**NUMA 的工程意义**：跨节点访存延迟翻倍、带宽受限。所以：`numactl --interleave`、`mbind`、`sched_setaffinity` 绑核 + 绑内存是高性能服务的标配。Kubernetes 的 **CPU Manager（static 策略）+ Topology Manager** 就是为解决"容器跨 NUMA 导致性能抖动"。

### 6.4 page cache：内存里最"不讲道理"的部分

```
read(fd, buf, n) 的真实路径
   │
   ▼
VFS: vfs_read → file->f_op->read_iter
   │
   ▼
page cache 查找 (inode->i_mapping->i_pages, 一颗 **xarray**)
   │
   ├─ 命中 → copy_to_user 直接拷贝 → 返回（**无磁盘 IO**）
   └─ 未命中 → 分配页 → 加入 page cache → 发起 readahead（预读） → 等待 IO 完成
                → 页标记 Uptodate → copy_to_user
```

| 概念 | 说明 |
|---|---|
| **address_space** | 一个文件（或块设备）在内存中的页集合，`mapping->i_pages` 用 xarray 索引（4.20 起替代 radix tree） |
| **脏页回写** | 写操作只改 page cache 并标脏；由 `flusher` 线程（`bdi` 每设备一个）按 `dirty_expire_centisecs`(30s)、`dirty_writeback_centisecs`(5s) 回写 |
| **脏页限流** | `dirty_ratio`（默认 20%，全局）/`dirty_background_ratio`（10%）；超限时**写进程自己被限流**（balance_dirty_pages），表现为"卡顿" |
| **直接回收** | 内存不够且 kswapd 追不上时，**申请内存的进程自己同步回收**（direct reclaim），表现为"分配变慢、抖动" |
| **预热** | `vmtouch`、`posix_fadvise(POSIX_FADV_WILLNEED)`、`readahead` |
| **清空** | `echo 3 > /proc/sys/vm/drop_caches`（线上慎用：会导致后续全部 major fault） |

**"为什么 Linux 内存看着用满了？"** —— page cache 是"可用内存"的一部分，不是泄漏。`free` 的 `available` 才是真实可用量。**这个误解出现在 90% 的初级运维事故里。**

### 6.5 内存回收：LRU 双链 + 二次机会

```
anon LRU                          file LRU
┌──────────┐  ┌───────────┐      ┌──────────┐  ┌───────────┐
│ active   │◄─┤ inactive  │      │ active   │◄─┤ inactive  │
└────┬─────┘  └─────┬─────┘      └────┬─────┘  └─────┬─────┘
     │ 冷热分层      │ 回收候选         │              │
     └──► 访问(PTE.A位)提升 ───────────┘              │
                                                    ▼
                                          回收时：干净页直接丢弃；
                                          脏页先回写再丢弃；代码页丢弃后从文件重读
基本配额（vm.swappiness 调节）: file:anon ≈ 1 : swappiness/100 量级
匿名页回收必须写 swap（否则无路可走 → OOM）
mlock 页、内核内存、被 pinned 的页不能回收
```

**`kswapd` vs 直接回收**：

| 机制 | 触发 | 行为 | 用户感受 |
|---|---|---|---|
| `kswapd`（每 node 一个） | 空闲页低于 `watermark[low]` | 后台异步回收 | 平滑 |
| 直接回收 | 分配时连 `min` 水位都不够 | 申请者自己回收 | **卡顿、P99 飙升** |
| OOM killer | 回收也救不回来 | 按 `oom_score` 杀进程 | 服务被杀 |

**watermark**：`min/low/high` 三档。低于 low 唤醒 kswapd，恢复到 high 才停；低于 min 直接回收。`/proc/zoneinfo` 可看水位和 `pages free`。

### 6.6 swap / zswap / zram

| 技术 | 说明 | 适用 |
|---|---|---|
| **swap 分区/文件** | 匿名页换出到磁盘 | 传统方案 |
| **zswap** | 换出前先在内存里压缩存放，压不下才落盘 | 内存中等、CPU 有余 |
| **zram** | 用压缩块设备当 swap（内存即"磁盘"） | 小内存设备、Android、容器 |
| **swapfile + swap cache** | 换出页在内存中还留副本，再次访问可能不用读盘 | 减少抖动 |

**`vm.swappiness`（0～100，默认 60）**：调节"回收匿名页 vs 丢弃文件页"的倾向。**注意**：它不是"是否使用 swap"的开关，设 0 也不代表不用 swap（只有在内存极度紧张时才会用）；数据库场景常设 1（尽量保留匿名页，丢弃干净的文件页更划算）。

### 6.7 Overcommit 与 OOM

```
overcommit_memory 策略
  0 (默认, 启发式): 估计"明显过量"才拒绝；大多数 malloc 都成功
  1 (总是): 来者不拒 → 完全依赖 OOM killer 兜底（Redis 推荐，因为 fork 需要大额虚拟内存）
  2 (严格): 不超过 CommitLimit = swap + ram×overcommit_ratio
```

**OOM killer 评分**：
```
oom_score ≈ f(RSS + swap + 页表占用)，并受 oom_score_adj(-1000..1000) 调整
日志: "Out of memory: Killed process 1234 (java) total-vm:..., anon-rss:..., file-rss:..."
```
**线上实践**：
1. `oom_score_adj` 给关键进程设 `-1000`（永不杀）；
2. **cgroup v2 的 `memory.max`** 让容器 OOM 只杀容器内进程（memcg OOM），不牵连宿主；
3. 配合 `memory.high`（软限，触发回收但不杀）+ PSI（`/proc/pressure/memory`）做预警。

**经典问题：Java 进程为什么"被 OOM 杀掉但没 HeapDump"？**
因为它是被**内核 OOM killer** 杀的（SIGKILL），不是 JVM 的 `OutOfMemoryError`。原因通常是：堆外内存（DirectByteBuffer、Metaspace、JNI、线程栈）增长导致 RSS 超限。排查要看 `dmesg` 的 OOM 日志和 `smaps`，而不是 GC 日志。

### 6.8 内存碎片与反碎片

| 碎片类型 | 定义 | 表现 |
|---|---|---|
| 内部碎片 | 分配单位大于需求（如 4KB 页里只放 100B） | SLUB 用 size class 缓解 |
| 外部碎片 | 空闲总量够，但没有连续大块 | 需要 order>0 分配时失败（如大页、DMA） |

**反碎片三招**：
1. **迁移类型分组**（MIGRATE_UNMOVABLE / MOVABLE / RECLAIMABLE），让不可移动的页别混进可移动区；
2. **内存规整（compaction）**：把可移动页搬走，腾出连续块（`/proc/sys/vm/compact_memory`、`kcompactd`）；
3. **尽早预留**：`hugetlb` 在启动时预留，避免运行期找不到大块。

## 第 7 章 进程内存布局与 mmap

### 7.1 一句话结论

> 进程看到的地址空间是**一张由 VMA（虚拟内存区域）拼成的地图**；真正决定"能不能访问"的是页表，真正决定"语义是什么"（堆/栈/文件映射）的是 VMA。

### 7.2 典型布局（x86-64）

```
高地址 0xFFFF_FFFF_FFFF_FFFF
        ┌───────────────────────────┐
        │ 内核空间（用户不可见）        │
0x0000_7FFF_FFFF_FFFF
        ┌───────────────────────────┐
        │ [stack] 主线程栈，向下增长    │  8MB 上限(ulimit -s)，
        │  ↓                        │  越界会扩张 VMA；超过 rlimit → SIGSEGV
        ├───────────────────────────┤
        │ [vvar] [vdso]  [vsyscall]  │
        ├───────────────────────────┤
        │ mmap 区域（共享库、匿名映射） │  ← 向上增长，glibc 的 malloc 大块走这里
        │  ↑                        │
        ├───────────────────────────┤
        │ [heap] brk 堆，向上增长      │
        ├───────────────────────────┤
        │ .bss  未初始化全局（零页）    │
        │ .data 已初始化全局            │
        │ .rodata 只读常量              │
        │ .text 代码（文件共享映射）     │
        └───────────────────────────┘
低地址 0x0000_0000_0000_0000
```

**用 `cat /proc/self/maps` 亲手验证**：会看到每行 `start-end perms offset dev inode pathname`，`perms` 是 `rwxp`，这就是 VMA 的 `vm_flags`。

### 7.3 VMA（vm_area_struct）与 maple tree

```c
struct vm_area_struct {
    unsigned long vm_start, vm_end;   // 区间
    struct mm_struct *vm_mm;
    pgprot_t vm_page_prot;            // 页保护（RWX）
    unsigned long vm_flags;           // VM_READ/WRITE/EXEC/SHARED/MAYWRITE/GROWSDOWN...
    struct file *vm_file;             // 文件映射时的 backing file（NULL=匿名）
    pgoff_t vm_pgoff;                 // 文件内偏移
    struct anon_vma *anon_vma;        // 匿名页反查（用于 rmap）
};
```

- 6.1 之前：进程所有 VMA 挂在一棵**红黑树** + 一条链表（链表用于顺序遍历）；
- 6.1 起：换成 **maple tree**（B 树变体，cache 友好，范围查询更快，且支持无锁读）。

**为什么需要 VMA**：缺页时要知道"这个地址该是什么"（匿名？文件？共享？可写？）。VMA 就是"地址空间的语义表"，页表只是"物理映射的事实表"。

### 7.4 mmap 的四种语义

| 组合 | 语义 | 典型用途 |
|---|---|---|
| **私有匿名** `MAP_PRIVATE\|MAP_ANONYMOUS` | 独立内存，初值全零，COW | malloc 大块、线程栈 |
| **共享匿名** `MAP_SHARED\|MAP_ANONYMOUS` | 父子/相关进程共享（本质是 tmpfs 上的匿名文件） | `fork` 前建共享缓冲、glibc arena |
| **私有文件** `MAP_PRIVATE` + file | 只读共享、写时 COW | 可执行文件 text、共享库 |
| **共享文件** `MAP_SHARED` + file | 多进程共享同一 page cache 页，写互相可见 | 共享内存、数据库 mmap 文件 |

**关键细节**：

```
mmap 并不立即分配物理内存，也不发起 IO
   │
   ├─ 只创建 VMA（可能合并相邻 VMA）
   ├─ 首次读 → filemap_fault → page cache（可能触发预读 readahead，一次读多页）
   ├─ 首次写私有映射 → COW
   └─ msync/fsync → 回写脏页

munmap 也不立即释放物理页
   └─ 只是解除映射，页的 refcount--；若为脏页且是 MAP_SHARED，仍在 page cache 中，
      由回写线程负责落盘。要确保落盘必须显式 msync/fsync。
```

**mmap 的坑**：
1. **SIGBUS**：映射了文件但文件被 truncate 到比映射小，访问越界页 → SIGBUS（不是 SIGSEGV）；
2. **小文件效率低**：mmap+write 的"3 次拷贝"优势需要大块连续 IO 才能体现，小文件反而不如 `read/write`；
3. **无法感知错误**：写入到 page cache 就"成功"了，磁盘错误要到回写时才暴露 → 数据库必须 `msync` + 校验；
4. **文件增长问题**：mmap 之后文件不会被自动扩容，写超出文件大小触发 SIGBUS。

### 7.5 malloc 背后的三层结构

```
malloc(32)      → tcache（线程本地，无锁，~几十 ns）
malloc(2KB)     → 线程 arena 的 bin（可能有锁，或 per-thread arena）
malloc(200KB)   → 超过 MMAP_THRESHOLD(默认128KB) → 直接 mmap（独立 VMA，free 时 munmap 归还内核）
free(大块)      → munmap，或 MADV_DONTNEED / MADV_FREE 延迟归还

glibc 关键机制：
  · arena：多线程时每线程尽量绑定独立 arena（上限 8×CPU 数），减少锁竞争
  · tcache：每线程 64 个 bin，每 bin 最多 7 个 chunk，无锁
  · 碎片：小对象频繁分配释放 → 用户态碎片（RSS 不降的常见原因）
  · 归还：glibc 默认"trim threshold"，MALLOC_TRIM_THRESHOLD_，可调 M_TRIM_THRESHOLD
高并发场景替换：tcmalloc / jemalloc / mimalloc（各自有 per-CPU/per-thread cache + size class）
```

**"为什么 free 了内存 RSS 不降？"** 标准答法：① 内存在用户态分配器（arena/tcache）里被缓存，未归还；② 归还了但内核没有立刻释放（`MADV_FREE` 惰性回收）；③ 碎片导致无法整块归还；④ 内存被 page cache 占用（文件映射）。排查看 `smaps` 的 `Heap`、`Anon`、`Mapped`，以及 `malloc_trim(0)` 的效果。

### 7.6 栈与栈溢出

| 细节 | 说明 |
|---|---|
| 主线程栈 | 由 execve 建立，大小 = `ulimit -s`（默认 8MB），VMA 标 `VM_GROWSDOWN` |
| 线程栈 | `pthread_create` 时 mmap 分配（默认 8MB 虚拟，按需提交），末尾有 **guard page**（不可访问，防越界踩别的映射） |
| 栈溢出检测 | 触发 guard page → SIGSEGV；或编译器插入 **stack canary**（`-fstack-protector`）检测栈上返回地址被改 |
| 用户态栈耗尽 | 死递归 → SIGSEGV，`dmesg` 里看到 "segfault at ... error 6 in libc" |
| 内核栈 | 16KB，不能递归太深；`CONFIG_VMAP_STACK` 后有 guard page，溢出立即报错而非静默破坏 |

## 第 8 章 并发与同步

### 8.1 一句话结论

> 并发错误来自三处：**CPU 乱序执行、编译器重排、多核并行**。同步机制的本质是：用"原子指令 + 屏障"把这三者约束住，让临界区看起来像串行执行。

### 8.2 为什么需要同步：一个例子拆到底

```c
// 线程 A: x = 1;      // 线程 B: y = 1;
//         r1 = y;              r2 = x;
// 直觉认为 r1==0 && r2==0 不可能（至少有一个先写）
// 但在真实硬件上完全可能发生：
//   ① 编译器把写操作延后/合并
//   ② CPU store buffer 让写"看起来没生效"
//   ③ 乱序执行把读提到写之前
// 这就是"内存可见性"问题
```

| 层级 | 会做什么"坏事" | 对策 |
|---|---|---|
| 编译器 | 重排、缓存到寄存器、消除"无用"读 | `barrier()` / `volatile`（仅防编译器，**不防 CPU**） |
| CPU | store buffer、乱序、投机 | `mfence`/`lock` 前缀、`smp_mb()` |
| Cache | 多核各自的 cache 副本不一致 | MESI 协议保证**最终**一致，但需要屏障确定顺序 |

**x86 的内存模型（TSO，Total Store Order）**：相对强，只允许"Store-Load 重排"；所以 x86 上很多 `smp_rmb()` 是空操作。**ARM/Power 是弱模型**，几乎任何重排都可能——这就是为什么"x86 上跑得好好的无锁代码，到了 ARM 服务器就出 bug"（如 Apple M 系列、鲲鹏、Ampere）。

**内存序语义（C++11 起的标准词汇）**：

| 语义 | 保证 | 类比 |
|---|---|---|
| `relaxed` | 只保证原子性，不保证顺序 | 计数器 |
| `acquire`（读） | 之后的读写不能重排到它之前 | 拿锁成功那一刻 |
| `release`（写） | 之前的读写不能重排到它之后 | 释放锁那一刻 |
| `acq_rel` | 两者兼具 | 原子 RMW |
| `seq_cst` | 全局单一全序（默认最安全最慢） | 强一致 |

**锁的本质**：`lock` 获取 = `acquire`，`unlock` 释放 = `release`。所以**"加锁保护的数据，在锁内都是可见的"**。

### 8.3 原子操作与 CAS

```
x86 的实现：
  · lock 前缀 + 指令（如 lock cmpxchg）→ 锁 cache line（不是锁总线！）
  · 早期 CPU 用总线锁，现代用"缓存锁"（MESI 的 Exclusive 状态下拿到独占权）
  · xchg 指令隐含 lock，不需要前缀

CAS (Compare-And-Swap):
  bool cas(T* p, T expected, T desired) {
      lock cmpxchg [p], desired   // 硬件保证原子
      // 返回是否成功，失败时把实际值写回 expected
  }
```

**CAS 循环（无锁栈 push）**：
```c
do { old = top; node->next = old; } while (!cas(&top, old, node));
```

**CAS 的三大问题**（面试高频）：
1. **ABA 问题**：值从 A→B→A，CAS 以为没变。解法：加版本号（`AtomicStampedReference`）、或 128 位 CAS（`cmpxchg16b`）、或改用 **hazard pointer/RCU** 避免复用。
2. **自旋开销**：高竞争下大量失败重试，CPU 白烧（可用 backoff、队列锁）。
3. **无法组合多个变量**：两个变量一起更新做不到原子（除非打包进一个 64/128 位字）。

### 8.4 锁家族全景（一张表决定选型）

| 机制 | 会睡眠？ | 可用在中断上下文？ | 适用场景 | 内核 API |
|---|---|---|---|---|
| **原子变量** | 否 | 是 | 计数、标志位 | `atomic_t`, `refcount_t` |
| **自旋锁** | 否（忙等） | **是**（必须用 `_irqsave` 版本） | 极短临界区；中断上下文 | `spin_lock` |
| **互斥锁** | **是** | 否 | 长临界区、可能睡眠 | `mutex_lock` |
| **读写锁** | 自旋版忙等 / 睡眠版 | 自旋版可以 | 读多写少 | `rwlock`, `rw_semaphore` |
| **seqlock** | 否 | 是 | 写极少、读极多且读方**可重试** | `write_seqlock`, `read_seqbegin` |
| **RCU** | 读方不睡眠；写方可以 | 读方可以 | 链表/路由表遍历（读多写少） | `rcu_read_lock` |
| **信号量** | 是 | 否 | 计数型资源池 | `down/up` |
| **完成量** | 是 | 否 | "等某事件完成" | `wait_for_completion` |
| **futex** | 用户态快路径无锁，慢路径睡眠 | — | 用户态锁的底层支撑 | 系统调用 |

**自旋锁的两个坑**：
1. **在单核上自旋无意义**：持有者无法被抢占去跑，只有关抢占才能保证前进（`spin_lock` 内部会 `preempt_disable()`）；
2. **中断上下文死锁**：
```
CPU0: 进程上下文 spin_lock(A)  ── 被中断打断 ──► 中断处理函数也 spin_lock(A) → 死锁！
解决：spin_lock_irqsave(&A, flags)  → 关本地中断再拿锁
（注意是"本地"中断，其他 CPU 上的中断照样能跑，所以锁本身仍需原子性）
```

**ticket spinlock → qspinlock**：
- ticket（next/owner 计数）保证 FIFO 公平，但所有等待者在**同一个 cache line 上转** → 缓存行弹跳（cache line bouncing），核多时性能雪崩；
- **qspinlock（MCS 队列锁）**：每个等待者在自己本地变量上自旋，只在**前驱**释放时被通知 → 极大减少总线流量。x86 从 4.x 起默认。

### 8.5 mutex 与 futex：用户态锁怎么不"每次都进内核"

```
pthread_mutex_lock 的快路径（无竞争）:
   ① 用户态 CAS: 0 (未锁) → 1 (已锁)   ← 纯用户态，几十 ns，**零系统调用**
   │ 成功 → 拿到锁，返回
   │ 失败（有竞争）
   ▼
   ② 慢路径: 置为 2（有等待者），调用 futex(FUTEX_WAIT, &futex_word, expected=2)
   ③ 内核: 哈希到 futex 桶 → 等待队列 → 睡眠（TASK_INTERRUPTIBLE）
pthread_mutex_unlock:
   ① 用户态 CAS: 1 → 0
   │ 失败（值为 2，说明有人在等）
   ▼
   ② futex(FUTEX_WAKE, 1) 唤醒一个等待者
```

**为什么这么设计（面试核心）**：绝大多数加锁**没有竞争**，如果每次都要进内核（几百 ns + 模式切换），锁的开销就毁了性能。futex 把"快路径"完全放到用户态，只在**真正需要等待**时才进内核。**这就是"AQS/ReentrantLock 在 Java 里、futex 在 C 里、都是同一套思路"**。

**futex 防丢失唤醒的关键**：`FUTEX_WIT(word, expected)` 里传 `expected` 值——内核会比较当前值是否仍等于 expected，不等就立即返回 `EAGAIN`。这避免了"检查后发现要睡，但锁在这期间被释放了"的经典丢失唤醒。

**mutex 的优化：乐观自旋（optimistic spinning）**：如果锁的持有者正在 CPU 上跑（`mutex_can_spin_on_owner`），先自旋一会儿而不是立刻睡——因为"睡下再唤醒"两次上下文切换的成本远大于自旋几十纳秒。这是 Linux mutex 相比 pthread 默认更快的原因之一。

### 8.6 读写锁、seqlock、RCU

**读写锁的问题**：读多写少时，写者可能被源源不断的读者**饿死**。Linux 的 `rwlock` 用"读者计数 + 写者优先位"缓解。

**seqlock（顺序锁）**：
```
写者: seq++ (变奇数) → 修改数据 → seq++ (变偶数)
读者: do { s1 = seq; if (s1 & 1) continue; 读数据; } while (s1 != seq_read_after());
特点: 读者完全不加锁、不阻塞写者 → 写者从不被饿死
代价: 读者可能重试；写者必须很快（不能睡眠）
应用: jiffies、timekeeping、vDSO 读时间
```

**RCU（Read-Copy-Update）** —— 面试深挖点：
```
读者: rcu_read_lock()（只是 preempt_disable，不是锁！）→ 遍历链表 → rcu_read_unlock()
写者: ① 复制新节点 ② 原子替换指针 ③ 等待宽限期(grace period) ④ 释放旧节点

宽限期: 等所有"已经开始的读者"都结束（synchronize_rcu / call_rcu）
为什么这么设计: 读者零开销（无原子操作、无 cache line 争用），
               而"链表遍历"这种读操作占了内核绝大多数场景（路由表、dentry、进程列表）
限制: 读者不能睡眠；旧的读者可能看到旧数据（最终一致，但对很多场景足够）
```

**RCU vs 读写锁（对比图）**：

| 维度 | rwlock | RCU |
|---|---|---|
| 读者开销 | 原子加/减计数（cache line 争用） | 几乎为零（仅关抢占） |
| 写者开销 | 等所有读者退出 | 复制 + 等宽限期（延迟高但可异步） |
| 读者能否睡眠 | 自旋版不能 | 不能 |
| 适合 | 读多写少、临界区较长 | 读极多写极少、指针替换型更新 |

### 8.7 死锁：四条件、四种策略、真实案例

```
死锁四必要条件（缺一不可）：
  ① 互斥      资源不能共享
  ② 持有并等待 拿着 A 等 B
  ③ 不可剥夺   别人不能抢走我的 A
  ④ 循环等待   A→B→C→A
```

| 策略 | 做法 | 代价 |
|---|---|---|
| **预防**（破坏条件） | 全局锁顺序（按地址排序加锁）、一次性申请全部资源、`trylock` 超时回退、锁分级 | 编程约束强、可能降低并发 |
| **避免**（动态检查） | 银行家算法（判断"分配后是否仍安全"） | 需预知最大需求，实际很少用 |
| **检测与恢复** | 资源分配图 + 环检测、`lockdep` 运行时图检测、`jstack` 找 Java 死锁 | 有检测开销 |
| **鸵鸟策略** | 不管（多数通用 OS 的选择） | 靠运维重启 |

**活锁 vs 饥饿 vs 死锁**：

| 名称 | 特征 | 例子 |
|---|---|---|
| 死锁 | 都停住，互相等 | 交叉加锁 |
| 活锁 | 都在动，但没进展 | 两个线程冲突后都退避重试，反复撞车 |
| 饥饿 | 某个线程永远排不上 | 低优先级 + 大量高优先级 |

**内核里的 lockdep**：`CONFIG_PROVE_LOCKING` 会记录"锁的获取顺序图"，一旦发现潜在环就打印 warning。这是内核开发/调优的利器，也是面试里"你怎么证明没有死锁"的加分答案。

### 8.8 伪共享（False Sharing）

```
两个变量 x, y 落在同一条 cache line（64B）
CPU0 改 x → 使 CPU1 的整条 line 失效（MESI 从 Shared → Invalid）
CPU1 改 y → 又要重新拉取整条 line
结果: 两个毫不相干的变量互相"打架"，性能可下降 3~10 倍
解法: ① 填充 padding 到 64B 对齐（__attribute__((aligned(64)))）
      ② 每线程独立变量 + 最后汇总（per-CPU 计数）
      ③ Java 的 @Contended / 数组填充
```

**验证手段**：`perf c2c`（cache-to-cache）能直接抓出伪共享热点，这是排查多线程性能问题的神技。

## 第 9 章 中断与异常

### 9.1 一句话结论

> 中断是**硬件打断 CPU 的唯一合法方式**，是操作系统"从被动等待变成事件驱动"的根基；也是内核代码里最需要小心（不能睡眠、不能长耗时）的地方。

### 9.2 中断 vs 异常 vs 系统调用

| 类别 | 来源 | 是否同步 | 例子 |
|---|---|---|---|
| **外部中断（硬件中断）** | CPU 外部设备 | 异步 | 网卡收包、键盘、时钟 tick、磁盘完成 |
| **不可屏蔽中断 NMI** | 硬件，几乎无法屏蔽 | 异步 | 内存 ECC 错误、看门狗、性能分析（perf/NMI watchdog） |
| **异常** | CPU 执行指令时产生 | **同步** | 缺页(#PF)、除零(#DE)、非法指令(#UD)、断点(#BP)、通用保护(#GP) |
| **软件中断** | `int n` 指令 | 同步 | 老式系统调用 `int 0x80` |

异常又分三类：**Fault（可恢复，如缺页，处理后重试指令）**、**Trap（如断点、`int3`，处理后执行下一条）**、**Abort（不可恢复，如机器检查异常）**。

### 9.3 一次硬件中断的完整旅程

```
① 网卡收到包 → DMA 写入内存 ring buffer → 触发 MSI-X 中断
   ▼
② CPU 在指令边界检查 INTR → 从 IDT 取向量 n 的门描述符
   （检查 CPL vs DPL、门类型）
   ▼
③ 硬件压栈：SS/RSP/RFLAGS/CS/RIP（可能还有 error code）
   从 TSS.RSP0（或 IST 栈）切换到**内核栈**
   （如果当前在用户态，还涉及 swapgs 换 GS 基址）
   ▼
④ 跳转到 asm 入口：common_interrupt → 保存其余寄存器(pt_regs) → call do_IRQ
   ▼
⑤ do_IRQ: 读中断控制器确认是哪个 IRQ
   （现代 x86 用 APIC/IOAPIC/MSI；老式 PIC 已被淘汰）
   → generic_handle_irq → handle_irq_event
   ▼
⑥ 执行**上半部（hardirq handler）**：关中断、不能睡眠、必须极快
   （典型：读状态寄存器、清中断标志、把数据搬到内存、标记下半部）
   ▼
⑦ irq_exit() → 若不在中断嵌套中且有待处理软中断 → invoke_softirq()
   ▼
⑧ 执行**下半部**：softirq / tasklet / workqueue / threaded irq
   ▼
⑨ iretq/sysret 返回被中断的上下文，恢复用户态或内核态
```

### 9.4 上半部与下半部（面试必问）

| 维度 | 上半部（hardirq） | 下半部（softirq/tasklet） | 下半部（workqueue） |
|---|---|---|---|
| 运行上下文 | 中断上下文 | 中断上下文（软中断） | **进程上下文（kworker 线程）** |
| 能否睡眠 | **绝对不能** | **绝对不能** | **可以** |
| 中断状态 | 本地 CPU 关中断 | 开中断 | 开中断 |
| 并发度 | 同一 IRQ 串行（同 CPU） | 同一类型可在多 CPU 并行 | 由工作队列并发管理 |
| 适合 | 确认硬件、清标志、极小拷贝 | 网络收包（NAPI）、定时器、RCU 回调 | 需要睡眠的工作：读磁盘、分配大内存、拿 mutex |

**为什么必须分两半**：
1. 上半部关中断 → 关太久会丢中断、增加延迟；
2. 上半部不能睡眠 → 但很多收尾工作需要睡眠（如 `kmalloc(GFP_KERNEL)`、`mutex_lock`）；
3. 中断上下文没有 `current->mm`（或借用的），**没有用户地址空间**，一旦睡眠就没法被正确唤醒调度。

**softirq 的固定 10 个类型**（不可动态新增，因为要保证性能与优先级）：
`HI_SOFTIRQ, TIMER_SOFTIRQ, NET_TX_SOFTIRQ, NET_RX_SOFTIRQ, BLOCK_SOFTIRQ, IRQ_POLL_SOFTIRQ, TASKLET_SOFTIRQ, SCHED_SOFTIRQ, HRTIMER_SOFTIRQ, RCU_SOFTIRQ`

**软中断的三个执行时机**：① `irq_exit` 返回时；② `ksoftirqd` 内核线程（防止软中断饿死用户进程）；③ 显式 `do_softirq()`（如网络 NAPI 轮询结束时）。

### 9.5 NAPI：中断 + 轮询的混合模式

```
传统模式（每包一中断）:
  10Gbps 网卡小包 → 每秒百万级中断 → CPU 全在进/出中断，活活打死（"中断风暴"）

NAPI 模式（中断触发 + 批量轮询）:
  ① 第一个包到 → 硬中断 → 关闭该网卡的接收中断 → 把设备挂到 poll_list → 触发 NET_RX 软中断
  ② 软中断里 napi_poll()：一次最多处理 budget（默认 64）个包，循环直到 ring 空或 budget 用尽
  ③ 若还有包 → 挂到 ksoftirqd 继续轮询（不重新开中断）
  ④ ring 空了 → 重新开启中断
关键参数: netdev_budget(300), netdev_budget_usecs(2000), 每轮 budget 64
效果: 把"百万次中断"变成"少量中断 + 批量处理"，同时保留低负载时的低延迟
```

**多核收包扩展**：`RPS`（软件分发到其他 CPU 的软中断）、`RFS`（按流亲和分发，保证同一连接在同一 CPU 处理，cache 友好）、`XPS`（发送侧选核）、`SO_REUSEPORT` + 多队列网卡 + IRQ 亲和性绑定。

### 9.6 中断相关的常见坑

| 问题 | 原因 | 排查/解法 |
|---|---|---|
| **关中断时间过长** | 驱动在上半部做了耗时操作 | `perf`/ftrace 看 `irq_handler_entry/exit` 时长；`/proc/interrupts` 看增长 |
| **一个 IRQ 打满一个核** | 单队列网卡、中断未分散 | `smp_affinity`、多队列、RPS |
| **软中断打满 CPU** | 网络流量大，`ksoftirqd` 跑满 | `top` 看 `si`（软中断）占比；调 `netdev_budget`、启用 GRO/GSO |
| **中断丢失** | 关中断期间事件被合并/丢弃 | 硬件有 pending 位；确保上半部简短 |
| **NMI watchdog 触发** | 某 CPU 长时间关中断（死循环/自旋锁死锁） | `dmesg` 找 "NMI watchdog: BUG: soft lockup"；`sysrq` 抓栈 |

**`si` 高 vs `sy` 高的区别**（排查必会）：`si`（softirq）高 → 网络/块设备中断后半部；`sy`（system）高 → 系统调用频繁（上下文切换、锁竞争、文件 IO）。

## 第 10 章 I/O 与零拷贝

### 10.1 一句话结论

> I/O 的性能问题，90% 可以归结为两个词：**拷贝次数** 和 **上下文切换次数**。零拷贝的本质就是**让数据在内核里"传引用"而不是"搬内容"**。

### 10.2 三种 I/O 方式

| 方式 | 机制 | CPU 占用 | 适用 |
|---|---|---|---|
| **轮询（Polling / PIO）** | CPU 死等状态寄存器 | 极高 | 极低延迟场景（DPDK 用户态轮询） |
| **中断驱动** | 设备完成后发中断 | 低（但有中断开销） | 通用（小块、随机 IO） |
| **DMA** | 设备直接读写内存，完成后中断 | 极低 | 大块传输（网卡、NVMe） |

**DMA 细节**：驱动准备好"描述符环"（descriptor ring），把物理地址写进设备寄存器，设备自己搬运数据，搬完发中断。现代系统还有 **IOMMU/SMMU**：把设备看到的地址也做一层翻译（设备直写恶意地址也打不到内核内存），并提供中断重映射（VT-d）。

**一致性与 cache**：DMA 直接改内存，可能与 CPU cache 不一致 → 需要 `dma_alloc_coherent`（非缓存/一致性映射）或显式 `dma_sync_single_for_cpu/device`（流式映射）。这是驱动开发的核心细节。

### 10.3 块设备栈：一次 read 到底走了多少层

```
read(fd) → VFS → file->f_op->read_iter
   │
   ├─ page cache 命中 → 直接返回（**不碰块层**）
   └─ 未命中 → 提交 bio
        ▼
   块层 (block layer)
     · blk-mq 多队列：每 CPU 一个软件队列 → 映射到硬件队列（NVMe 支持 64K 队列）
     · IO 调度器：none(mq-deadline/kyber/bfq)
        - NVMe/SSD: 通常用 none（设备自己并行，调度反而添乱）
        - HDD: mq-deadline（合并相邻请求、减少寻道）
     · 合并（merge）：相邻扇区的 bio 合并成大请求
        ▼
   驱动 (nvme/scsi/virtio-blk) → 填描述符 → 敲门铃寄存器
        ▼
   设备 DMA 读 → 完成中断 → 唤醒等待者 → 页标记 Uptodate
```

**块层关键概念**：

| 概念 | 说明 |
|---|---|
| **bio** | 一次 I/O 的基本单位（含一组页 + 扇区范围） |
| **request** | 调度器管理的请求（可合并多个 bio） |
| **队列深度 QD** | 同时在飞的请求数；SSD 靠高 QD 打满 IOPS |
| **IOPS vs 吞吐** | 4K 随机看 IOPS，大块顺序看 MB/s；SSD 的"随机 4K"是它的强项，HDD 是灾难 |
| **写放大** | SSD 的 FTL、文件系统的 COW/日志都会导致实际写入 > 逻辑写入 |
| **fio** | 压测工具：`fio --rw=randread --bs=4k --iodepth=32` |

### 10.4 零拷贝：四种方案的拷贝次数对比

**基线：传统 `read` + `write`（4 次拷贝 + 4 次态切换）**

```
① DMA: 磁盘 → 内核 page cache          （拷贝1，DMA）
② CPU: page cache → 用户缓冲区          （拷贝2，CPU）  ← read 返回
③ CPU: 用户缓冲区 → socket 发送缓冲区    （拷贝3，CPU）  ← write 进入
④ DMA: socket buffer → 网卡             （拷贝4，DMA）
同时: read 两次态切换 + write 两次态切换 = 4 次
```

| 方案 | 拷贝次数 | 态切换 | 原理 | 限制 |
|---|---|---|---|---|
| **read+write** | 4（2 次 DMA + 2 次 CPU） | 4 | 基线 | — |
| **mmap + write** | 3（省掉拷贝2） | 4 | 用户态直接映射 page cache 页，write 直接从 page cache 拷到 socket buffer | 小文件效率低；文件被截断会 SIGBUS；映射/解除映射有开销 |
| **sendfile** | **2（纯 DMA）** | **2** | 内核直接把 page cache 页"挂"到 socket buffer（若网卡支持 SG-DMA，则连 CPU 拷贝都省了） | 不能修改数据（不能加密/压缩）；只能用于"文件→socket" |
| **splice** | **0 CPU 拷贝** | 2（+ pipe） | 通过 pipe 在两个 fd 间移动**页引用**（不拷内容） | 需要 pipe 作为中介 |
| **io_uring / 用户态零拷贝** | 0（true zero-copy） | 极低 | 共享内存环形队列提交/收割，或 RDMA 直接写远端内存 | 编程复杂、需内核版本支持 |

**sendfile 细节（面试常追问）**：
```c
sendfile(out_fd /*socket*/, in_fd /*file*/, &offset, count);
// 内核里: do_splice_direct → 把 page cache 的页引用加入 socket 的 skb
// 若网卡支持 scatter-gather DMA（几乎所有现代网卡都支持）：
//   数据可以"散着"从多个 page cache 页直接 DMA 到网卡，无需 CPU 合并
// 这就是 nginx 配置 sendfile on 后静态文件性能提升的原因
```

**为什么 nginx 用 sendfile 而某些场景不用**：需要 gzip 压缩、加密、改写内容时，必须落到用户态处理，零拷贝就用不上（nginx 会退化成 read+write）。

### 10.5 落盘一致性：write 返回 ≠ 数据在磁盘

```
write() 返回成功 → 数据只在 **page cache（内存）** 里
   │  （进程崩溃：数据还在，page cache 归内核，不丢）
   ▼
fsync(fd) / fdatasync(fd)：
   · fsync: 刷数据 + 元数据（inode 大小、mtime、间接块）
   · fdatasync: 只刷数据 + 必要元数据（更快）
   · 还会下发 FLUSH/FUA 命令，把磁盘/SSD 的**写缓存**也刷掉
   ▼
O_SYNC / O_DSYNC：每次 write 都同步（极慢，慎用）
direct IO (O_DIRECT)：绕过 page cache 直写设备（数据库自管缓存时用，要求对齐）
```

**掉电一致性的三层**：① page cache → ② 磁盘控制器缓存（有电池/超级电容才安全）→ ③ 盘片/NAND。企业级盘用 **FUA（Force Unit Access）** 保证直写介质。**这就是为什么"数据库必须 fsync"以及"机械盘 fsync 要 ms 级"**。

**日志（journal / WAL）的作用**：先写日志再改数据（write-ahead logging），崩溃后重放日志恢复。ext4 的 `data=ordered`（默认）保证"数据先于元数据落盘"，避免崩溃后出现"元数据指向未写入数据的空洞"。

## 第 11 章 网络 I/O 模型

### 11.1 一句话结论

> 服务器能扛多少连接，取决于**"等待数据"这件事由谁来做**：一个线程等一个连接（阻塞）→ 1 万连接要 1 万线程；一个线程等一万个连接（多路复用）→ 1 个线程就够。

### 11.2 五种 I/O 模型（必背图）

```
                    ┌────────────────────────────────────────┐
阻塞 I/O            │ 发起 → 等数据 → 等数据就绪 → 拷贝 → 返回 │  全程阻塞
                    └────────────────────────────────────────┘
                    ┌────────────────────────────────────────┐
非阻塞 I/O          │ 发起 → 立刻返回 EAGAIN → 轮询 → 拷贝   │  轮询浪费 CPU
                    └────────────────────────────────────────┘
                    ┌────────────────────────────────────────┐
I/O 多路复用        │ select/epoll 阻塞在"多个 fd"上 →        │  单线程管多连接
                    │ 就绪 → 逐个 read（拷贝仍阻塞）           │  ★主流方案
                    └────────────────────────────────────────┘
                    ┌────────────────────────────────────────┐
信号驱动 I/O        │ 注册 SIGIO → 数据就绪发信号 → read      │  几乎不用
                    └────────────────────────────────────────┘
                    ┌────────────────────────────────────────┐
异步 I/O (io_uring) │ 提交请求 → 立刻返回 → 完成后通知/收割    │  真异步（无阻塞阶段）
                    └────────────────────────────────────────┘

前 4 种都是"同步 I/O"（因为拷贝数据阶段仍需自己完成/等待），只有最后一种是真正异步。
```

### 11.3 select / poll / epoll 对比（面试最高频）

| 维度 | select | poll | epoll |
|---|---|---|---|
| fd 上限 | **1024**（`FD_SETSIZE` 编译期固定） | 无上限（链表） | 无上限（红黑树） |
| 事件集合传递 | 每次调用**全量拷贝** fd_set 到内核 | 每次全量拷贝 | **一次注册，长期有效**（`epoll_ctl`） |
| 就绪检测 | 内核**线性遍历**所有 fd（O(n)） | O(n) | **回调机制**，就绪时挂到链表（O(1) 感知） |
| 返回后 | 用户要自己遍历找就绪的 fd | 同 | 直接返回就绪链表（O(k)，k=就绪数） |
| 触发模式 | 仅水平触发（LT） | 仅 LT | **LT + ET** |
| 跨平台 | POSIX 通用 | POSIX | Linux 专有（BSD 用 kqueue） |
| 适合 | 少量连接 | 少量～中等 | **海量连接（C10K/C100K）** |

**epoll 的三件套与内核数据结构**：

```
epoll_create1()  → 创建 eventpoll 对象
                     ┌─────────────────────────────┐
                     │ struct eventpoll            │
                     │  · rbr: 红黑树（注册的 fd）    │  ← epoll_ctl ADD 插入
                     │  · rdllist: 就绪链表          │  ← 事件触发时挂入
                     │  · wq: 等待队列（epoll_wait 睡在这）│
                     └─────────────────────────────┘
                          ▲                    │
epoll_ctl(ADD)  ──────────┘                    │
   把"回调"注册到目标 file 的 poll 队列:          │
   eppoll_entry → ep_poll_callback              │
                                               ▼
数据到达 → 网卡中断 → 协议栈 → sock_def_readable
   → 调用 wait queue 上注册的回调 → ep_poll_callback
   → 把该 fd 的 epitem 挂到 rdllist → 唤醒 epoll_wait
```

**为什么 epoll 高效**：**它把"遍历"换成了"回调"**。100 万个连接里只有 10 个活跃，select 每次要检查 100 万，epoll 只处理那 10 个。

**LT vs ET（必考）**：

| 模式 | 通知行为 | 编程要求 |
|---|---|---|
| **水平触发 LT**（默认） | 只要 fd 还有数据可读，`epoll_wait` 就**一直返回**它 | 可以不一次读完，简单安全 |
| **边缘触发 ET** | 只在"状态变化"那一刻通知**一次**，没读完的数据不会再通知 | **必须循环 read 到 `EAGAIN`**，且 fd **必须设为非阻塞**（否则最后一次 read 会永久阻塞） |

**ET 的三个坑**：
1. 必须非阻塞 fd；
2. 必须读到 `EAGAIN`（用 `recv(..., MSG_DONTWAIT)` 或非阻塞 fd）；
3. `accept` 也要循环（一次可能多个连接就绪），否则会丢连接。

**惊群（thundering herd）**：
- 现象：多个进程/线程阻塞在同一个 listen fd 上，新连接到来时**全部被唤醒**，只有一个 accept 成功，其余白醒；
- 解法：① `EPOLLEXCLUSIVE`（4.5+，内核只唤醒一个）；② `SO_REUSEPORT`（每个进程一个独立 listen socket，内核按哈希分流，同时提升多核扩展性）；③ 单线程 accept + 分发（Redis/Nginx 多进程模型）。

### 11.4 Reactor 与 Proactor

```
Reactor（epoll 是它的核心组件）:
  事件循环: epoll_wait → 就绪 → 分发 handler → handler 自己做 read（可能有阻塞）
  变体:
    · 单 Reactor 单线程（Redis）：简单、无锁、但无法利用多核，且一个慢命令阻塞全部
    · 单 Reactor 多线程（Netty 早期）：IO 在 reactor 线程，业务在线程池
    · 主从 Reactor（Netty/nginx 主流）：
        mainReactor 只管 accept → subReactor（多个）各管一批连接的读写 → 业务线程池

Proactor（io_uring / Windows IOCP）:
  提交异步请求 → 内核做完（包括数据拷贝）→ 完成事件 → handler 只处理结果
  优势: 无"就绪后还要自己读"的阶段，减少系统调用与线程切换
```

| 维度 | Reactor | Proactor |
|---|---|---|
| 谁做 IO | 应用自己（就绪后 read/write） | 内核做（真正的异步） |
| 系统调用次数 | 多（epoll_wait + read + write） | 少（提交 + 收割） |
| 编程复杂度 | 中 | 高（缓冲区生命周期管理） |
| 代表 | epoll + Netty/Redis/nginx | io_uring、IOCP |

### 11.5 io_uring：Linux 异步 IO 的答案

```
用户态                          内核态
┌──────────────┐              ┌──────────────────────┐
│ SQ ring (提交)│──mmap 共享──►│  io_uring 实例        │
│  · SQE 数组   │              │  · 解析 SQE          │
│ CQ ring (完成)│◄─mmap 共享───│  · 投递给 io-wq 或     │
│  · CQE 数组   │              │    在提交路径内联完成   │
└──────────────┘              └──────────────────────┘

关键特性:
  ① 单次 io_uring_enter 可提交**批量**请求（数组），摊销系统调用成本
  ② SQPOLL 模式：内核线程轮询 SQ ring，用户态**零系统调用**
  ③ registered buffers/files：预注册，避免每次请求重复 pin 页/查 fd 表
  ④ linked SQEs：链式依赖（如 read → write，串行执行）
  ⑤ 支持 read/write/accept/connect/send/fsync/fallocate/openat...
  ⑥ 真正的异步：连 page cache miss 的磁盘 IO 也不阻塞提交者
性能: 高 IOPS 场景下比 epoll + read 快 2~5 倍（减少 syscall 与拷贝）
代价: 学习曲线陡、缓冲区生命周期管理复杂（内核可能在用你的 buffer）
```

**为什么 io_uring 是"未来"**：它把"每操作一次系统调用"变成"批量提交 + 批量收割"，同时统一了文件 IO 和网络 IO（epoll 只能做网络/pipe 的就绪通知，磁盘文件 epoll 永远返回就绪，必须用阻塞 read 或 AIO）。

### 11.6 socket 在内核里是什么

```
fd ──► struct file (f_op = socket_file_ops) ──► struct socket ──► struct sock
                                                                   │
                    ┌──────────────────────────────────────────────┘
                    ▼
        TCP 层 (tcp_sock) → IP 层 → 网卡驱动 → 硬件
        每层用 sk_buff 传递；数据从 socket 接收缓冲区(sk_receive_queue) 到用户态
关键缓冲参数（调优必知）:
   net.core.rmem_max / wmem_max        ← 单 socket 上限
   net.ipv4.tcp_rmem / tcp_wmem (min default max)  ← TCP 自动调优区间
   net.core.somaxconn                   ← accept 队列上限（配合 listen backlog）
   net.ipv4.tcp_max_syn_backlog         ← 半连接队列
   net.ipv4.tcp_tw_reuse                ← TIME_WAIT 复用（客户端）
内存压力: 接收缓冲占用内核内存（不在进程 RSS 里），大量连接会吃光内存 → 需要 limit
```

**`listen` 的两个队列**（高频细节）：
1. **SYN 队列（半连接）**：收到 SYN、回了 SYN-ACK、还没收到 ACK；
2. **accept 队列（全连接）**：三次握手完成，等待应用 `accept`。
`backlog` 影响的是 accept 队列；SYN flood 攻击打的是 SYN 队列（可用 `syncookies` 防）。

## 第 12 章 文件系统

### 12.1 一句话结论

> 文件系统是"把块设备变成一个**有名字、有层次、有元数据**的键值存储"的那一层；VFS 则是让 Linux 能同时容纳 ext4、XFS、NFS、proc、tmpfs 的**统一抽象层**。

### 12.2 VFS 的四个核心对象

| 对象 | 代表什么 | 生命周期 | 关键字段 |
|---|---|---|---|
| **super_block** | 一个已挂载的文件系统实例 | 挂载到卸载 | `s_fs_info`（具体 FS 私有数据）、`s_op`、`s_root` |
| **inode** | 一个文件（**不含名字**） | 打开/缓存期间，引用计数 | `i_ino`, `i_mode`, `i_size`, `i_nlink`, `i_mapping`(page cache), `i_op`, `i_fop` |
| **dentry** | 一个**目录项**（名字 → inode 的映射） | 挂在 dentry cache | `d_name`, `d_inode`, `d_parent`, `d_op` |
| **file** | 一个**打开的文件实例**（进程级） | `open` → `close` | `f_pos`（读写偏移）, `f_flags`, `f_op`, `private_data`, `f_count` |

```
        路径 "/home/a.txt"
              │
    ┌─────────▼─────────┐
    │ dentry cache (dcache)│  名字 → inode 的哈希表 + LRU
    │  "/" → "home" → "a.txt"
    └─────────┬─────────┘
              ▼
    ┌───────────────────┐        ┌──────────────────────┐
    │ inode (a.txt)      │───────►│ page cache (i_mapping)│
    │ 元数据 + i_size     │        │  文件数据页            │
    └─────────┬─────────┘        └──────────────────────┘
              ▼
    ┌───────────────────┐
    │ 具体 FS (ext4/xfs) │  → 块层 → 磁盘
    └───────────────────┘
```

**路径解析流程**（面试可讲）：`link_path_walk` 逐段解析，优先走 **RCU walk**（无锁查 dcache），命中则免锁；未命中则加锁查/调用 `i_op->lookup`。`.` 和 `..` 特殊处理，符号链接递归解析（有深度上限 40 防环）。

### 12.3 inode 与磁盘布局（ext4 为例）

```
ext4 磁盘布局（把设备切成若干 block group，每组类似一个小型文件系统，减少寻道）
┌──────────┬──────────┬─────────────────────────────────┐
│ Boot     │ Super    │ Block Group 0 | BG 1 | BG 2 ... │
│ (1KB)    │ Block    │ ┌──────────────────────────────┐│
└──────────┴──────────┴─│ Super Block 副本 (备份)         ││
                        │ Group Descriptor 表            ││
                        │ Block Bitmap（块是否已用）      ││
                        │ Inode Bitmap（inode 是否已用）  ││
                        │ Inode Table（所有 inode 实体）   ││
                        │ Data Blocks（文件内容）          ││
                        └──────────────────────────────┘│
```

**inode 里有什么**：`mode`（类型+权限）、`uid/gid`、`size`、`atime/mtime/ctime`、`nlink`（硬链接数）、`blocks`（占用块数）、块指针（ext4 用**extent 树**，早期 ext2/3 用三级间接指针）。

**经典计算题：三级间接寻址的最大文件大小**
```
假设块大小 4KB，块指针 4 字节 → 每块可存 1024 个指针
12 个直接块            ：12 × 4KB           = 48KB
1 个一级间接（1024 指针）：1024 × 4KB        = 4MB
1 个二级间接            ：1024² × 4KB        = 4GB
1 个三级间接            ：1024³ × 4KB        = 4TB
合计 ≈ 4TB（+ 4GB + 4MB + 48KB）
```
这也是为什么 ext3 单文件上限约 4TB、ext4 用 extent（`ext4_extent` 记录"起始块 + 连续长度"）后能到 16TB（4K 块）且大文件元数据更少。

### 12.4 硬链接 vs 软链接

| 维度 | 硬链接 `ln a b` | 软链接 `ln -s a b` |
|---|---|---|
| 本质 | 目录项指向**同一个 inode** | 新建一个 inode，内容是**目标路径字符串** |
| inode | 相同 | 不同 |
| `nlink` | 增加 | 不影响 |
| 删原文件 | 数据仍在（nlink 减到 0 才真删） | 变成"悬空链接"（dangling） |
| 跨文件系统 | **不可以** | 可以 |
| 链接目录 | **不允许**（防环） | 允许 |
| `ls -l` 显示 | 普通文件 | `l` 类型 + `-> target` |

### 12.5 写文件到底写了什么（面试常问"写一个文件的过程"）

```
open(path, O_CREAT|O_WRONLY) → 创建 inode（分配 inode 位图位）+ dentry + file
   ▼
write(fd, buf, n) → copy_to_user 反方向：用户 buf → page cache 页
                    （若文件是新扩展的，先分配块/延迟分配 delayed allocation）
                    页标脏（PG_dirty），加入回写队列
   ▼
（异步）flusher 线程 → writeback → 提交 bio → 块层 → 磁盘
   ▼
fsync → 等待回写完成 → 下发 FLUSH → 更新日志
   ▼
close → f_count-- → 最后一个引用关闭时才真正释放 struct file
```

**稀疏文件**：`seek` 到 1TB 处写 1 字节，文件大小显示 1TB，但 `du` 只占 4KB（未分配的块不占空间，读返回 0）。这解释了"`ls -l` 大小和 `du` 不一致"。

### 12.6 三张表与 fd 的本质（最容易被问倒）

```
进程 A                                     进程 B
┌──────────────────┐                     ┌──────────────────┐
│ files_struct     │                     │ files_struct     │
│  fdtable:        │                     │  fdtable:        │
│   fd 0 ─────────┐│                     │   fd 0 ──────┐   │
│   fd 1 ───────┐ ││                     │   fd 1 ──────┤   │
│   fd 2 ─────┐ │ ││                     │   ...        │   │
└─────────────┼─┼─┼┘                     └──────────────┼───┘
              │ │ │                                     │
              ▼ ▼ ▼                                     ▼
        ┌──────────────────────────────────────────────────┐
        │ 系统级打开文件表 (struct file，每个 open 一个，引用计数) │
        │  file#1: f_pos, f_flags, f_op, f_count            │
        │  file#2: ...                                      │
        └──────────────────────────┬───────────────────────┘
                                   ▼
        ┌──────────────────────────────────────────────────┐
        │ inode 表（每个文件一个，全局缓存）                     │
        │  i_ino, i_size, i_mode, i_nlink, i_mapping         │
        └──────────────────────────────────────────────────┘
```

**由此推出的经典结论**：

| 操作 | 结果 |
|---|---|
| `fork` | 子进程**复制 fd 表**（指向同样的 `struct file`，`f_count++`）→ **父子共享同一个文件偏移** `f_pos`！ |
| `open` 两次同一个文件 | 两个独立的 `struct file` → **各自的偏移**，互不影响 |
| `dup(2)` | 复制 fd 表项，指向**同一个** `struct file` → **共享偏移** |
| `close(fd)` | `f_count--`，减到 0 才真正关闭（其他 dup/fork 出来的仍可用） |
| 一个进程退出 | 它的 fd 表释放，`f_count` 相应减少 |
| 删掉正在打开的文件 | `unlink` 只是 `nlink--` 并删 dentry，inode 要等 `f_count` 和 `nlink` 都为 0 才释放（**"文件已删除但空间不释放"的原因**） |

**"文件描述符耗尽"**：`ulimit -n`（`RLIMIT_NOFILE`）限制每进程 fd 数；`/proc/sys/fs/file-max` 是系统级上限；ss/netstat 看不到泄漏的 fd，要看 `ls /proc/<pid>/fd | wc -l`。

### 12.7 崩溃一致性：日志与 COW

| 方案 | 代表 | 原理 | 优点 | 缺点 |
|---|---|---|---|---|
| **写前日志 WAL（journal）** | ext4(JBD2)、XFS | 先写日志（记录"将要做的元数据变更"），再写实际位置；崩溃后重放 | 成熟、恢复快 | 写放大（元数据写两次） |
| **写时复制 COW** | btrfs、ZFS | 从不覆盖旧数据，新数据写到新块，最后原子更新根指针 | 天然支持快照、校验和、无写放大元数据 | 碎片化、随机写放大 |
| **软更新 soft updates** | FFS | 精心安排写入顺序，避免不一致 | 无日志开销 | 实现复杂 |

**ext4 的三种日志模式**：
- `journal`（最安全最慢）：数据也写日志（写两次）；
- `ordered`（默认）：**数据先落盘，再提交元数据日志**——保证"元数据不会指向未写入的数据";
- `writeback`（最快最不安全）：只记元数据日志，数据可能晚于元数据落盘（崩溃后可能读到旧数据/空洞）。

**原子性技巧**：`rename()` 在同一文件系统内是原子的（更新目录项指针）——这是"配置文件原子更新"的标准做法（写临时文件 → fsync → rename）。

### 12.8 其他关键点

| 主题 | 要点 |
|---|---|
| **tmpfs** | 基于内存+swap 的伪文件系统，`/dev/shm`、`/run`；读写不落盘，重启消失；`size=` 限制（默认内存一半） |
| **procfs/sysfs** | `/proc` 暴露进程与内核参数（`/proc/sys` 可写即调参），`/sys` 暴露设备与驱动模型（kobject/attribute） |
| **overlayfs** | 联合挂载：`lowerdir`（只读层）+ `upperdir`（可写层）+ `merged`；写时 **copy-up**（把文件从下层拷到上层再改）；容器的镜像分层就是它 |
| **NFS** | 网络文件系统；`hard mount` 时服务器无响应 → 进程进入 **D 状态**，这是"D 状态堆积"的经典原因 |
| **ext4 vs XFS** | XFS 大文件/大目录/并发写更强（B+ 树索引），ext4 兼容性好、小文件元数据操作成熟；数据库/大文件场景多选 XFS |
| **挂载** | `mount` 本质是把 super_block 挂到某个 dentry 上；`mount namespace` 让每个容器看到不同的挂载树 |
| **文件系统缓存三级** | dentry cache（名字）、inode cache（元数据）、page cache（数据）——**`echo 3 > drop_caches` 三者全清** |

## 第 13 章 容器与虚拟化

### 13.1 一句话结论

> **容器不是虚拟机，而是"被内核限制了视野和配额的普通进程"**：namespace 决定"你能看到什么"，cgroup 决定"你能用多少"，rootfs 决定"你能执行什么"。

### 13.2 容器的四块拼图

```
┌─────────────────────────────────────────────────────────────┐
│                    容器 = 一个普通 Linux 进程                  │
├─────────────────────────────────────────────────────────────┤
│ ① namespace（8 种）  视野隔离：pid/net/mnt/uts/ipc/user/cgroup/time │
│ ② cgroup（v2）       资源配额：cpu.max / memory.max / io.max    │
│ ③ rootfs + overlayfs 文件系统隔离：镜像分层 + copy-up           │
│ ④ 安全边界           capabilities 裁剪 / seccomp-bpf / AppArmor/SELinux │
│                      user namespace 做 uid 映射（容器 root ≠ 宿主 root）│
└─────────────────────────────────────────────────────────────┘
```

**八种 namespace**（面试常考"容器隔离靠什么"）：

| namespace | 隔离内容 | 标志 | 效果 |
|---|---|---|---|
| **PID** | 进程 ID 空间 | `CLONE_NEWPID` | 容器内看到自己是 pid 1；无法看到宿主进程 |
| **NET** | 网络栈（网卡、路由表、iptables、端口） | `CLONE_NEWNET` | 独立 IP、独立端口空间 |
| **MNT** | 挂载点 | `CLONE_NEWNS` | 独立挂载树，可实现 rootfs 替换 |
| **UTS** | hostname / domainname | `CLONE_NEWUTS` | 独立主机名 |
| **IPC** | System V IPC、POSIX 消息队列 | `CLONE_NEWIPC` | 独立共享内存/信号量 |
| **USER** | uid/gid 映射 | `CLONE_NEWUSER` | 容器内 root 映射成宿主普通用户（**最重要，没有它容器 root 就是宿主 root**） |
| **CGROUP** | cgroup 视图 | `CLONE_NEWCGROUP` | 看不到宿主的 cgroup 层级 |
| **TIME**（6.6+） | 系统时钟偏移（monotonic/boottime） | `CLONE_NEWTIME` | 每容器不同时间基准 |

**注意：容器内的 `ps` 看不到别的进程，但 `/proc` 里仍然有内核信息**——这正是"容器共享内核"的直接体现，也是为什么容器逃逸漏洞（内核漏洞）会影响整个宿主机。

### 13.3 cgroup v2

```
统一层级（v2 只有一棵树）:
/sys/fs/cgroup/
├── cgroup.controllers            ← 这个 cgroup 可用的控制器
├── cgroup.subtree_control        ← 向下启用的控制器
├── <group>/
│   ├── cpu.max                   ← "quota period"，如 "50000 100000" = 0.5 核
│   ├── cpu.weight                ← 相对权重（1-10000，默认 100）
│   ├── memory.max                ← 硬限，超了触发 memcg OOM
│   ├── memory.high               ← 软限，超了限流+回收但不杀
│   ├── memory.current            ← 当前用量
│   ├── io.max                    ← "8:16 rbps=... wbps=... riops=... wiops=..."
│   ├── pids.max                  ← 进程数上限（防 fork 炸弹）
│   └── cpuset.cpus / cpuset.mems ← 绑核/绑 NUMA
```

| cgroup v1 vs v2 | v1 | v2 |
|---|---|---|
| 层级 | 每控制器一棵树 | 统一一棵树 |
| 权重的意义 | `cpu.shares` 相对份额 | `cpu.weight` 更强的一致性语义 |
| 内存 | `memory.limit_in_bytes` | `memory.max`/`memory.high`/`memory.low`（更有层次） |
| 压力指标 | 无 | **PSI**（`cpu.pressure`/`memory.pressure`/`io.pressure`） |
| 线程粒度 | 难 | 支持 threaded 模式 |

**PSI（Pressure Stall Information）** 是重要的工程改进：它能告诉你"有多少时间是因为资源不足而被迫等待"，比传统的利用率更贴近用户体验（`some avg10=...` 表示至少一个任务被阻塞的时间占比）。

### 13.4 镜像分层与 overlayfs

```
镜像（只读层，按 Dockerfile 指令一层层叠加）
┌──────────────────────┐  ← layer 4: COPY app /
├──────────────────────┤  ← layer 3: RUN pip install
├──────────────────────┤  ← layer 2: ENV
├──────────────────────┤  ← layer 1: FROM ubuntu
└──────────────────────┘
        +
┌──────────────────────┐
│ 容器可写层 (upperdir) │  ← 所有修改都写在这里，容器删除即丢失
└──────────────────────┘
        ↓ overlayfs 合并视图（merged）
   容器内看到的是一个完整文件系统

写文件流程: 目标在下层 → **copy-up**（整文件复制到上层）→ 修改上层副本
  影响: 修改大文件很贵；容器可写层不能无限增长（要监控）
```

**"为什么容器启动快"**：不用装系统、不用启动 init 服务，只是 `clone()` 一个进程 + 挂载 rootfs，毫秒级。**"为什么容器镜像小"**：分层复用，多个镜像共享基础层。

### 13.5 虚拟机 vs 容器（对比表，必背）

| 维度 | 虚拟机（VM） | 容器 |
|---|---|---|
| 隔离级别 | **硬件级**（Hypervisor 虚拟出 CPU/内存/设备） | **内核级**（namespace + cgroup） |
| 内核 | 每 VM 一个独立内核 | **共享宿主内核** |
| 启动时间 | 秒～分钟 | 毫秒～秒 |
| 资源开销 | 每 VM 有完整 OS（GB 级） | 只是进程（MB 级） |
| 密度 | 单机几十个 | 单机数百～数千 |
| 安全性 | 强（Hypervisor 是硬件抽象层，攻击面小） | 较弱（内核漏洞可逃逸） |
| 迁移/快照 | 成熟 | 相对弱 |
| 适用 | 多租户、强隔离、异构内核 | 微服务、CI/CD、弹性扩缩容 |
| 代表 | KVM、Xen、VMware | Docker、containerd、Kata、gVisor |

**安全增强方向**：
- **Kata Containers**：容器外壳 + 轻量 VM 内核（每个容器一个 VM）；
- **gVisor**：用户态内核（拦截系统调用自己实现），牺牲性能换隔离；
- **Firecracker**：AWS 的 microVM，~125ms 启动，兼顾隔离与密度。

### 13.6 硬件虚拟化的关键机制（VM 为什么现在这么快）

| 机制 | 说明 |
|---|---|
| **VT-x / AMD-V** | CPU 提供"根模式/非根模式"，guest 执行敏感指令时触发 **VMExit** 陷入 Hypervisor，处理完 **VMEntry** 返回 |
| **EPT / NPT（二级页表）** | 以前用"影子页表"（shadow page table）维护 guest 页表 → 宿主页表的映射，极其复杂且慢；EPT 让硬件做两级翻译（GVA→GPA→HPA），几乎零软件开销 |
| **VPID** | 给 TLB 项打 VM 标签，切 VM 不用刷 TLB |
| **virtio** | 半虚拟化设备：guest 知道自己被虚拟化，用共享内存 **vring** 环形队列 + 通知机制通信，比模拟真实硬件（e1000）快得多 |
| **SR-IOV** | 网卡硬件切分成多个 VF，直通给 VM，绕过 Hypervisor 数据面 |
| **VMCS** | 保存 VM 与 vCPU 的状态（寄存器、控制字段） |

**VMExit 是最贵的操作**（微秒级），所以现代虚拟化的优化方向都是"减少 VMExit"：批处理、APIC 虚拟化、posted interrupt、嵌套页表。

## 第 14 章 观测与性能排查

### 14.1 排查的四步法

```
① 定性：是 CPU、内存、IO、网络，还是锁/调度？
   先看: top / vmstat 1 / iostat -x 1 / sar -n DEV 1 / pidstat 1
② 定位到进程/线程：top -H -p <pid> 看哪个线程；pidstat -t
③ 定位到代码：perf top / perf record + 火焰图 / strace / ltrace
④ 验证假设：改一个变量，前后对比（A/B），别靠猜
```

### 14.2 关键指标速查

| 工具/指标 | 含义 | 异常信号 |
|---|---|---|
| `top` 的 `us/sy/si/wa/id` | 用户态/内核态/软中断/等 IO/空闲 | `sy` 高=系统调用多；`si` 高=网络中断；`wa` 高=IO 瓶颈 |
| `vmstat` 的 `r/b` | 运行队列/阻塞(D 状态)进程数 | `r` 远大于核数 = CPU 排队；`b` 多 = IO 卡住 |
| `vmstat` 的 `cs` | 上下文切换次数 | 每秒数万～数十万 = 锁竞争或线程过多 |
| `vmstat` 的 `si/so` | swap 换入/换出 | 非 0 且持续 = 内存不足，性能悬崖 |
| `iostat -x` 的 `%util`、`await`、`aqu-sz` | 设备利用率、平均等待、队列长度 | `await` 高 + `%util` 100% = 设备饱和；SSD 上 `%util` 不准（并行度高） |
| `free` 的 `available` | **真实可用内存** | 只有这个才代表"还能用多少" |
| `/proc/pressure/*` | PSI 压力 | `some avg60` 持续 > 10% = 有资源争抢 |
| `ss -s` / `netstat -s` | 连接数、重传、丢包 | `retrans` 增长 = 网络质量差 |

### 14.3 六大经典场景（面试场景题的高频原型）

**场景 1：CPU 使用率 100%，怎么查？**
```
① top 看是 us 还是 sy 高
② us 高 → top -H 找出线程 → perf top 看热点函数 → 可能是死循环、正则回溯、GC
③ sy 高 → 系统调用多：strace -c -p <pid> 统计，常见是频繁 read/write（无缓冲）、futex 争锁
④ si 高 → 软中断：网络流量大或中断未分散（RPS/多队列）
⑤ 若 top 看不到高 CPU 进程 → 可能是中断/内核线程（ksoftirqd、kworker）
```

**场景 2：load average 很高，但 CPU 很闲？**
> 因为 Linux 的 load 包含 **D 状态（不可中断睡眠）**进程。查 `vmstat` 的 `b` 列、`ps -eo state,pid,comm | grep D`。常见原因：磁盘/网络存储（NFS）卡住、驱动 bug、大量同步 IO。**这是一个"必须知道"的面试题**。

**场景 3：内存持续上涨，是泄漏吗？**
```
① 看 free 的 available 和 /proc/meminfo 的 MemAvailable
② 看进程 RSS：ps -o rss；/proc/pid/smaps_rollup 看 Anon/File/Shmem 构成
③ 是内核还是用户态？slabtop 看内核 slab（dentry/inode 泄漏很常见）
④ 是 page cache 吗？file 占比大且可回收 → 正常
⑤ 用户态泄漏：valgrind / heaptrack / jemalloc profiling / pprof
⑥ 容器内：memory.current、memory.stat（anon/file/slab/kernel）
```

**场景 4：服务 P99 抖动，CPU/内存都不高**
```
候选原因排查顺序：
① 直接回收（direct reclaim）→ /proc/vmstat 的 allocstall 增长
② THP compaction 抖动 → /proc/vmstat 的 thp_fault_alloc / compact_stall
③ 磁盘 IO 尖刺 → iostat 看 p99 await
④ 锁竞争 → perf lock / off-CPU 火焰图
⑤ CPU 被限流（cgroup cpu.max 用尽）→ cpu.stat 的 nr_throttled / throttled_time
⑥ 邻居干扰（其他容器抢 IO/内存带宽）→ PSI 的 io/cpu pressure
```

**场景 5：大量 TIME_WAIT / CLOSE_WAIT**
| 现象 | 原因 | 处理 |
|---|---|---|
| **TIME_WAIT 多** | 主动关闭方要等 2MSL（保证最后的 ACK 被收到、旧报文不干扰新连接） | 客户端：`tcp_tw_reuse=1`；用连接池；服务端尽量让**客户端先关** |
| **CLOSE_WAIT 多** | 对方已关，本端应用**没调 close**（代码 bug / 连接池泄漏） | 查代码是否漏 close；不是内核参数能解决的 |

**场景 6：容器里 `free` 显示内存被吃满**
> 容器里的 `free` 读的是**宿主机**的 `/proc/meminfo`（因为没做 meminfo 虚拟化）。正确做法：看 cgroup 的 `memory.current`/`memory.max`，或 `memory.stat`。这是"容器里监控指标不可信"的经典例子。

### 14.4 eBPF：内核可观测性的核武器

```
传统工具: 预先埋点的静态指标（/proc、tracepoint 固定）
eBPF:     在**运行时**往内核任意函数/事件挂一段"受验证的字节码"

工作流程:
  ① 用户态把 eBPF 程序加载进内核
  ② **verifier** 检查: 无非法内存访问、无死循环（有界循环）、栈不超限、不睡眠
  ③ JIT 编译成机器码（性能接近原生）
  ④ 通过 map（哈希/数组/ringbuf）与用户态交换数据
常用工具链: bcc（Python 封装）、bpftrace（一行脚本）、Cilium（网络）、Falco（安全）
经典用例:
  · off-CPU 火焰图（谁在等、等多久）——传统 perf 只能看 on-CPU
  · 追踪任意函数延迟（kprobe + 时间戳）
  · 网络丢包定位（XDP/tc 层）
  · 安全审计（syscall 监控）
```

**为什么 eBPF 是"安全的内核编程"**：不用加载内核模块（不会因为一行空指针让整机 panic），验证器保证内存安全 + 有界执行，且可以热插拔。

### 一、进程与线程（8 题）

#### Q1 进程和线程的区别是什么？★★★☆☆
**归属**：字节跳动、阿里、腾讯、美团（几乎全行业）

**标准回答（分层递进）**：
1. **资源角度**：进程是资源分配的基本单位（地址空间、文件表、信号处理、凭证）；线程是 CPU 调度的基本单位（寄存器 + 栈）。
2. **地址空间**：进程独立；同进程线程共享地址空间（堆、全局变量、代码），各自独立栈和寄存器。
3. **开销**：创建（fork 要复制页表/VMA/文件表）、切换（是否换 CR3/刷 TLB）、通信（进程要 IPC，线程直接读写共享变量但需要同步）。
4. **健壮性**：一个线程段错误会拖垮整个进程（共享地址空间），进程之间互相隔离。
5. **Linux 实现**：两者都是 `task_struct`，差异在 `clone()` 的 `CLONE_VM/CLONE_FILES/CLONE_SIGHAND/CLONE_THREAD` 标志。

**深入加分**：说清"切换开销"的真实构成——线程切换省的是"地址空间切换"（CR3 + TLB），但 cache 污染依旧；进程切换还多了文件表切换（`switch_mm` + `switch_to`）。

**追问链条**：
- "线程共享了什么、私有什么？" → 见 3.7 表格
- "一个线程能修改另一个线程的栈吗？" → 能（同一地址空间，只要有指针），这正是线程不安全的根源
- "为什么说线程崩溃会拖垮进程？" → 信号（SIGSEGV）是按线程组投递的，默认动作是终止整个进程

---

#### Q2 fork 为什么返回两次？写时复制怎么实现的？★★★★☆
**归属**：腾讯、字节、快手

**过程**：
1. `copy_process` 复制 `task_struct`、分配内核栈、复制/共享资源；
2. `copy_mm` 复制页表，**把所有私有可写页的 PTE 改成只读**，物理页 `_refcount++`；
3. `copy_thread` **构造子进程的内核栈帧**：让 `pt_regs->ax = 0`，返回地址指向"从系统调用返回用户态"的路径；
4. 父进程正常返回（返回值=子 pid），子进程被调度后沿构造好的栈返回（返回值=0）。

**COW 触发链**：写只读 PTE → `#PF` → `do_wp_page` → `_refcount==1` 则复用（零拷贝），否则 `alloc_pages + copy_page` → 改 PTE 可写 → 旧页 `_refcount--`。

**延伸追问**：
- "fork 之后父子谁先跑？" → 不确定，由调度器决定（可人为干预，但通常子进程优先被唤醒）；
- "vfork 为什么危险？" → 共享地址空间，子进程改栈会踩坏父进程；
- "Redis bgsave 用 fork，有什么风险？" → COW 导致内存翻倍（写多的场景），且 fork 本身在超大内存进程上要复制页表（几十 ms 停顿）。

#### Q3 线程切换和进程切换的代价差在哪？★★★★☆
**归属**：阿里、字节

**答**：进程切换要做 `switch_mm`（换 CR3），导致 TLB 失效（现代用 PCID 缓解，只失效自己的项而不是全局刷）；线程切换同一地址空间，**不换 CR3**。其余成本（寄存器、栈、调度器、cache 污染、分支预测器污染）两者相同。

**量化**：直接成本 1～3μs，间接（cache/TLB 冷）可达 2～10μs。`vmstat cs` 可观测。

**追问**："为什么线程多反而慢？" → 上下文切换变多、cache 局部性变差、锁竞争加剧、调度开销（O(log n) 的树操作 + 负载均衡）。

#### Q4 进程间通信有哪些方式？各自适用场景？★★★☆☆
**归属**：美团、百度、京东

| 方式 | 原理 | 拷贝次数 | 适用 |
|---|---|---|---|
| 管道 pipe | 内核环形缓冲区（默认 64KB/16 页），半双工 | 2（写一次读一次） | 父子进程、shell 管道 |
| 命名管道 FIFO | 文件系统里的特殊文件 | 2 | 无亲缘关系进程 |
| 消息队列 | 内核链表，有类型 | 2 | 结构化消息、可异步 |
| 共享内存 shm | 同一物理页映射到两个进程 | **0**（最快） | 大数据量、需要自己同步 |
| 信号量 | 内核计数器 | — | 同步手段（常配共享内存） |
| 信号 signal | 内核投递，异步 | — | 事件通知（不能传数据） |
| socket | 内核协议栈 | 2+ | 跨主机、通用 |
| Unix domain socket | 内核 socket，无协议栈开销 | 2 | 本机 C/S，性能优于 TCP 回环 |
| eventfd / memfd | 轻量通知/内存文件 | 0/2 | 高性能框架（如 QEMU、容器运行时） |

**加分**：`mmap` + 共享内存是"零拷贝 IPC"，但要自己做同步（用 futex 或信号量）；Java 的 `MappedByteBuffer`、RocketMQ 的存储都是这条路。

#### Q5 僵尸进程和孤儿进程的区别？怎么处理？★★★☆☆
**归属**：腾讯、小米

**答**：
- 僵尸：子进程已退出，父进程未 `wait`，PCB 未释放（只占极少内核资源，但占 pid）。`kill -9` 无效，只能杀父进程或让父进程 `wait`。预防：`signal(SIGCHLD, SIG_IGN)` 或正确 `waitpid`。
- 孤儿：父进程先退出，子进程被 `init(1)` 或 `subreaper` 收养，最终被回收，无危害。
- **容器场景**：pid 1 必须是能"收割僵尸"的 init（tini、systemd），否则容器里会积累僵尸——这是"容器需要一个 init 进程"的根因。

#### Q6 协程为什么比线程轻？Go 的 GMP 怎么调度？★★★★☆
**归属**：字节（Go 技术栈）、腾讯、B 站

**答要点**：
1. 协程在**用户态**切换：只保存少量寄存器 + 换栈，**不进内核**（几十 ns vs 微秒）；
2. 栈小且可增长（Go 初始 2KB vs 线程 8MB 虚拟）；
3. GMP：G=协程，M=内核线程，P=逻辑处理器（本地 runq 256）；work stealing、handoff（M 阻塞时把 P 让出）、netpoll（epoll 就绪回填）、sysmon 抢占（1.14+ 信号式异步抢占）；
4. 代价：不能像线程一样"随便阻塞"（阻塞系统调用会 handoff，但也消耗 M）；调试复杂（栈不连续）。

**追问**："协程能利用多核吗？" → 能，M:N 模型下多个 M 并行跑在不同核；但 N:1 模型不能。

#### Q7 一个进程最多能创建多少线程？受什么限制？★★☆☆☆
**归属**：阿里、快手

**答**：不是单一因素，是**多个上限取最小**：
1. 虚拟地址空间：每线程默认 8MB 栈（`pthread_attr_setstacksize` 可调小），32 位进程 3GB 用户空间 → 约 380 个；64 位几乎不受此限；
2. `RLIMIT_NPROC`（每用户进程/线程数）、`/proc/sys/kernel/threads-max`（系统级）、`pid_max`；
3. 内核内存：每线程一个 `task_struct` + 16KB 内核栈 → 1 万线程约 200MB+ 内核内存；
4. cgroup 的 `pids.max`；
5. 实际瓶颈常是**调度与锁竞争**，而不是硬上限。

**追问**："1 万线程的系统有什么问题？" → 上下文切换风暴、内存开销、调度延迟、锁竞争、`cs` 指标飙升。正确做法是 reactor + 线程池。

#### Q8 进程的虚拟地址空间布局是怎样的？★★★☆☆
**归属**：美团、滴滴

**答**：低→高：`.text`（代码，文件共享映射）→ `.rodata` → `.data` → `.bss`（零页）→ heap（brk 向上）→ mmap 区（向下，共享库/匿名映射）→ 栈（向下增长，8MB）→ `[vvar][vdso]` → 内核空间（用户不可见）。用 `/proc/self/maps` 可验证。

**加分**：讲清"为什么共享库放中间"——mmap 区向上/向下都能扩展，避免和 heap/stack 抢空间；以及 ASLR 会随机化各段基址（安全）。

### 二、内存管理（9 题）

#### Q9 虚拟内存的作用是什么？★★★★★
**归属**：全行业必考

**答**（五点，见 5.2）：隔离、抽象（连续空间）、按需分配、共享、超额分配（配合 swap/COW）。再补一句"让程序不必关心物理布局，也让操作系统能在进程间安全地复用物理内存"。

**追问**："不用虚拟内存行不行？" → 早期 DOS 就是物理地址，问题是无法隔离、无法重定位、无法按需加载；嵌入式 MCU 仍有部分无 MMU 系统（用 MPU 做区域保护）。

#### Q10 多级页表解决了什么问题？为什么是 4 级？★★★★★
**归属**：字节、阿里、腾讯、美团

**答**：
1. **空间问题**：单级页表要覆盖整个虚拟地址空间，32 位下每进程 4MB 页表（1024×1024×4B），64 位更是天文数字；多级页表**只为实际用到的区域分配页表页**，稀疏空间几乎零成本。
2. **为什么 4 级**：48 位虚拟地址 = 9+9+9+9+12，每级 512 项正好放进 4KB 页（512×8B=4KB）。级数由"地址位宽 + 页大小 + PTE 大小"唯一确定。5 级（57 位，LA57）用于超大内存机器。
3. **代价**：一次访存要多次查表 → 用 TLB 摊销；大页让高层表项直接终止（PS 位）。

**追问**："页表项里有哪些位？" → P/RW/US/A/D/PS/NX + 物理页框号（见 5.3 表）。"Accessed/Dirty 谁置的？" → 硬件自动置，内核回收时读它做 LRU 判断，读完清零。

---

#### Q11 TLB 是什么？为什么进程切换会影响性能？★★★☆☆
**归属**：阿里、华为

**答**：TLB 是 MMU 内的页表项缓存（L1 分 i/dTLB，L2 STLB 共享）。命中 ~10 cycle，未命中要 page walk（4 次访存，串行依赖）。
进程切换时 VA→PA 映射变化 → TLB 必须失效 → 后续大量 miss。
**现代缓解**：PCID/ASID 打标签（只失效自己的项）；大页减少项数需求；`invlpg` 精确失效单页；批量 shootdown 用 IPI。

**深挖**："多核下改页表要注意什么？" → TLB shootdown（IPI 广播），大量 `munmap` 会成为瓶颈。

---

#### Q12 缺页中断的完整处理流程？minor 和 major 的区别？★★★★★
**归属**：字节、美团、腾讯、快手

**答**：见 5.5 流程图。要点：
1. `#PF` 带 error code（P/W/U/RSVD/I）；
2. 查 VMA（maple tree）判断合法性，非法 → SIGSEGV；
3. 分配页表项 → 分流：匿名页零页、文件页查 page cache、COW 复制、共享页映射；
4. minor（无 IO，~1μs）vs major（要读盘，几十 μs～ms）。

**追问**：
- "为什么第一次 malloc 不占物理内存？" → 只建 VMA，读时映射零页，写时才分配；
- "为什么缺页会引发磁盘 IO 风暴？" → 大量 major fault + 预读不足；用 `madvise(WILLNEED)`、预读调优、mmap 预热（`vmtouch`）；
- "缺页会发生在内核态吗？" → 会（`vmalloc` 区未建映射、copy_from_user 触碰未映射页），但内核态缺页不能随便睡眠/杀进程，处理更严格。

---

#### Q13 用户态和内核态怎么切换？系统调用过程？★★★★★
**归属**：全行业

**答**：见 2.3。必须讲清：`syscall` 指令 → MSR（LSTAR/STAR/FMASK） → 切栈（TSS.rsp0）→ `entry_SYSCALL_64` 保存 pt_regs → 查 `sys_call_table` → 执行 → `sysretq` 返回。
**加分**：KPTI 导致切页表、vDSO 避免系统调用、参数用 r10 的原因、返回值范围约定。

---

#### Q14 物理内存分配器怎么设计的？伙伴系统和 slab 的区别？★★★★☆
**归属**：阿里、字节（基础架构岗更爱问）

**答**：
- 伙伴系统：管**页框**，按 2 的 order 管理，分配时劈半、释放时与"伙伴"合并（只有对齐的相邻块才是伙伴），解决外部碎片（合并可行），但仍会有碎片。
- SLUB：管**小对象**，为每种对象建 kmem_cache，per-CPU current slab 无锁分配，对象内嵌 freelist，复用已初始化的对象（省 clear/构造）。
- 层次：`kmalloc` → SLUB → 伙伴 → 物理页。
- 补充：pcp（per-CPU page list）用于单页快速分配。

**追问**："内存碎片怎么解决？" → 迁移类型分组 + compaction + 大页预留（见 6.8）。

---

#### Q15 内存不足时会发生什么？OOM killer 怎么选进程？★★★★☆
**归属**：腾讯、美团、滴滴

**答**：
1. 空闲页低于 low 水位 → 唤醒 `kswapd` 异步回收（回收 page cache、匿名页换出 swap）；
2. 低于 min → **直接回收**（申请者自己同步回收，表现为卡顿）；
3. 回收无效 → OOM killer 按 `oom_score`（RSS+swap+页表，受 `oom_score_adj` 影响）杀进程；
4. cgroup 场景 → memcg OOM，只杀容器内进程。

**追问**："Java 进程被 OOM killer 杀掉，为什么没有 heapdump？" → 是内核 SIGKILL，不是 JVM OOM；通常是堆外内存（DirectByteBuffer/JNI/线程栈/Metaspace）导致 RSS 超限，看 `dmesg` 和 `smaps`。

---

#### Q16 page cache 是什么？为什么 Linux 内存总显示"用满"？★★★★☆
**归属**：阿里、字节、快手

**答**：page cache 是文件数据在内存中的缓存（`address_space` + xarray），读命中免磁盘 IO，写先改内存再异步回写（脏页）。
"用满"是误解：`free` 的 `buff/cache` 是可回收的，`available` 才是真实可用。`drop_caches` 会清空导致后续全 major fault。
**深挖**：脏页限流（`dirty_ratio`）、回写线程（flusher）、`fsync` 的作用、`O_DIRECT` 绕过的适用场景。

---

#### Q17 malloc 是怎么实现的？free 之后内存去哪了？★★★☆☆
**归属**：字节、腾讯

**答**：glibc 三层：tcache（无锁）→ arena bin（有锁/per-thread arena）→ 大块 mmap（>128KB 阈值，`M_MMAP_THRESHOLD`）。底层靠 `brk`（扩展 heap）和 `mmap`（独立映射）。
`free` 不归还内核：进入空闲 bin 复用；大块可 `munmap`；也可 `MADV_DONTNEED/MADV_FREE` 惰性归还。RSS 不降的四个原因见 7.5。

**追问**："为什么多线程 malloc 会慢？" → arena 锁竞争 + 伪共享 + 碎片；解法 tcmalloc/jemalloc（per-thread cache + size class）。

### 三、并发与同步（7 题）

#### Q18 什么是死锁？四个必要条件？怎么预防？★★★★★
**归属**：全行业

**答**：四条件（互斥、持有并等待、不可剥夺、循环等待），破坏任意一个即可预防：
1. **固定锁顺序**（按地址/ID 排序加锁）；
2. **一次性申请全部资源**（或 `trylock` + 回退释放）；
3. **超时**（`trylock(timeout)`，失败则回滚）；
4. **锁分级/分段**（减少交叉）；
5. 检测：`lockdep`、`jstack`、资源分配图找环。

**追问**："活锁和饥饿呢？" → 见 8.7 对比表。

---

#### Q19 自旋锁和互斥锁的区别？什么时候用哪个？★★★★★
**归属**：字节、阿里、腾讯

| 维度 | 自旋锁 | 互斥锁 |
|---|---|---|
| 等待方式 | 忙等（占 CPU） | 睡眠（让出 CPU） |
| 上下文 | 可用于中断上下文 | 不能用于中断上下文 |
| 临界区 | 极短（纳秒～微秒级） | 可能较长、可能睡眠 |
| 单核 | 无意义（需关抢占） | 正常 |
| 内核 API | `spin_lock` / `spin_lock_irqsave` | `mutex_lock` |

**关键坑**：进程上下文拿自旋锁时若被中断打断，中断处理函数再拿同一把锁 → 死锁，所以要用 `_irqsave` 版本关本地中断。

#### Q20 什么是 CAS？ABA 问题怎么解决？★★★★☆
**归属**：阿里、字节、美团

**答**：CAS 是硬件原子指令（`lock cmpxchg`），比较并交换，是无锁算法的基础。
ABA：值 A→B→A，CAS 认为没变。解法：
1. 加版本号（`AtomicStampedReference`）；
2. 128 位 CAS（`cmpxchg16b`）；
3. 延迟回收/RCU/hazard pointer（不重用地址）；
4. 避免"值复用"的设计（如用唯一 ID）。

**延伸**："CAS 自旋在高竞争下有什么问题？" → 大量失败重试、cache line 争用、可能比锁更慢；解法：队列锁（MCS/qspinlock）、backoff、分段。

---

#### Q21 内存屏障是什么？volatile 能代替吗？★★★★☆
**归属**：字节、华为、阿里

**答**：屏障约束 CPU/编译器的重排。`volatile` 只保证"不被优化掉、每次从内存读"，**不保证原子性、不保证多核可见性顺序**（在 x86 上碰巧很多场景能用，但在 ARM 上会出问题）。
正确做法：`std::atomic` + `memory_order`（acquire/release/seq_cst），或内核的 `smp_mb/rmb/wmb` + `READ_ONCE/WRITE_ONCE`。

**加分**：讲 x86-TSO 与 ARM 弱内存模型的差异，以及"为什么 x86 上写得好的代码移植到 ARM 会崩"。

---

#### Q22 futex 是什么？为什么用户态锁快？★★★★☆
**归属**：字节、腾讯（高级岗）

**答**：futex = fast userspace mutex。无竞争时纯用户态 CAS（零系统调用）；有竞争才 `FUTEX_WAIT` 进内核睡眠，释放时 `FUTEX_WAKE`。
核心是"**快路径不进内核**"——绝大多数加锁无竞争，若每次都进内核（数百 ns），锁就毁了性能。
细节：`FUTEX_WAIT` 传 expected 值防丢失唤醒；内核按地址哈希到 futex 桶；PI futex 支持优先级继承。

---

#### Q23 RCU 的原理？和读写锁比优势在哪？★★☆☆☆
**归属**：字节、阿里（内核/基础架构）

**答**：读侧 `rcu_read_lock` 只是关抢占（零原子操作），写侧"复制-替换指针-等宽限期-释放旧数据"。读侧几乎零开销、不阻塞写者、写者不饿死。
代价：读者可能看到旧数据（最终一致）；读者不能睡眠；宽限期可能很长。
适用：链表/哈希表遍历（路由表、dentry、进程列表）。

---

#### Q24 什么是伪共享？怎么发现和解决？★★★☆☆
**归属**：字节、快手、腾讯

**答**：多个核修改同一 cache line 的不同变量 → MESI 反复失效 → 性能降数倍。
发现：`perf c2c`；解决：padding 对齐 64B、per-thread/per-CPU 变量 + 汇总、`@Contended`。
**加分**：MESI 四态（Modified/Exclusive/Shared/Invalid）与"为什么写要拿独占权"。

### 四、I/O 与网络（8 题）

#### Q25 零拷贝是什么？sendfile 为什么快？★★★★★
**归属**：字节、阿里、腾讯、美团、快手

**答**：见 10.4。传统 read+write：4 次拷贝（2 DMA + 2 CPU）+ 4 次态切换；sendfile：2 次 DMA + 2 次态切换（网卡支持 SG-DMA 时 CPU 拷贝为 0）。
原理：内核把 page cache 的**页引用**挂到 socket buffer（skb 的 frags），不拷贝内容；网卡用 scatter-gather DMA 直接从多个页取数据。
**追问**："mmap+write 和 sendfile 怎么选？" → 需要修改数据用 mmap（但仍 3 次拷贝），纯转发用 sendfile；小文件 mmap 反而更慢。

---

#### Q26 select/poll/epoll 的区别？epoll 为什么高效？★★★★★
**归属**：全行业（后端必考）

**答**：见 11.3 表格。核心三句：
1. select 有 1024 限制 + 每次全量拷贝 + O(n) 遍历；
2. epoll 用 `epoll_ctl` 一次注册（红黑树），内核用**回调**在事件发生时把 fd 挂到就绪链表，`epoll_wait` 只返回就绪的（O(k)）；
3. LT/ET 的区别与 ET 必须非阻塞 + 读到 EAGAIN。

**追问**：
- "epoll 一定能比 select 快吗？" → 连接少且都活跃时，epoll 的回调注册/维护开销反而更大；
- "epoll 是异步 IO 吗？" → 不是，它是**就绪通知**（同步多路复用），read 仍可能阻塞；
- "百万连接怎么配？" → `ulimit -n`、`somaxconn`、内存（每连接内核缓冲）、`epoll` + 多线程/多进程（SO_REUSEPORT）。

---

#### Q27 LT 和 ET 的区别？ET 为什么要非阻塞？★★★★☆
**归属**：字节、腾讯、美团

**答**：LT 只要缓冲区有数据就一直通知；ET 只在状态变化时通知一次。ET 必须循环读到 `EAGAIN` 才知道读完了，若 fd 阻塞，最后一次 read 会永远阻塞 → 必须非阻塞。另外 `accept` 也要循环。

---

#### Q28 一次网络请求从网卡到应用，经过哪些层？★★★☆☆
**归属**：阿里、字节

**答**：网卡 DMA → 硬中断（NAPI）→ 软中断 NET_RX → 链路层 → IP 层（路由/分片重组）→ TCP 层（排序/ACK/滑动窗口）→ socket 接收队列 → 唤醒等待者（epoll 回调）→ 应用 read（copy_to_user）。发送侧对称：write → TCP 分段 → IP → qdisc → 驱动 → DMA。
**加分**：讲 GRO/GSO/TSO（批量合并减少 CPU 包处理）、checksum offload、RSS 多队列。

---

#### Q29 阻塞/非阻塞、同步/异步的区别？★★★★☆
**归属**：腾讯、美团

**答**：
- 阻塞/非阻塞：**调用是否立即返回**（数据没准备好时）；
- 同步/异步：**数据拷贝由谁完成**（同步要自己等/做拷贝，异步是内核做完通知你）。
组合：阻塞+同步（默认 read）、非阻塞+同步（轮询 read）、多路复用+同步（epoll）、异步（io_uring/IOCP）。**epoll 属于"同步非阻塞 + 多路复用"，不是异步 IO。**

---

#### Q30 io_uring 相比 epoll 优势在哪？★★☆☆☆
**归属**：字节、阿里（中间件/存储岗）

**答**：真异步 + 批量提交 + 共享内存环（mmap）免拷贝 + SQPOLL 免系统调用 + 统一文件/网络 IO。epoll 只能做就绪通知，且磁盘文件永远"就绪"（必须阻塞 read 或 AIO）。
代价：缓冲区生命周期、内核版本要求、调试复杂。

---

#### Q31 write 返回成功，数据一定落盘了吗？★★★★☆
**归属**：阿里、腾讯、字节（存储/DB 方向必考）

**答**：不是。write 只写进 page cache。要落盘需 `fsync`（数据+元数据）/`fdatasync`（数据+必要元数据），并下发 FLUSH 刷设备缓存。`O_DIRECT` 绕过 page cache 但要求对齐。掉电一致性三层：page cache → 设备缓存 → 介质。数据库必须 fsync（或 WAL + 组提交优化）。

---

#### Q32 磁盘 IO 慢怎么排查？★★★☆☆
**归属**：美团、滴滴、快手

**答**：`iostat -x 1` 看 `await`/`aqu-sz`/`%util`；`iotop` 找进程；`blktrace`/`bpftrace` 看块层延迟分布；区分顺序/随机、队列深度、是否被限流（cgroup io.max）；SSD 注意写放大与 GC；检查是否有大量 major fault、page cache 未命中、fsync 频繁。

### 五、文件系统（7 题）

#### Q33 inode 是什么？里面有什么？★★★★☆
**归属**：腾讯、阿里、百度

**答**：inode 是文件的**元数据实体**（不含名字）：`mode/uid/gid/size/times/nlink/blocks/数据块指针(extent)`。名字在 dentry 里。`df -i` 看 inode 用量（inode 耗尽是"磁盘没满但写不进去"的经典原因）。
**追问**："inode 数量怎么定？" → 格式化时按 `-i`（每多少字节一个 inode）或 `-N` 指定，ext4 默认每 16KB 一个；大量小文件场景要调大。

---

#### Q34 硬链接和软链接的区别？★★★☆☆
**归属**：百度、小米、京东

**答**：见 12.4 表格。补充：硬链接不能跨 FS、不能链目录（防环）；软链接可跨、可悬空；删原文件硬链接仍可用（nlink>0）。

---

#### Q35 打开一个文件，内核里发生了什么？三张表的关系？★★★★★
**归属**：字节、腾讯、阿里

**答**：见 12.6 图。`open` 创建 `struct file`（或复用），fd 表项指向它；inode 全局缓存。由此推出：
- `fork` 共享 `struct file` → **共享文件偏移**；
- `dup` 同；
- 独立 `open` → 独立偏移；
- `unlink` 已打开文件 → 空间不释放直到 `f_count` 归零。
**追问**："为什么多个线程读同一 fd 会错乱？" → 共享 f_pos，需要各自 open 或加锁/`pread`。

---

#### Q36 ext4 的日志机制？掉电会怎样？★★★★☆
**归属**：阿里、腾讯（DB/存储）

**答**：JBD2 写前日志：先写描述块+元数据到 journal 并提交，再写回实际位置；崩溃后重放（replay）。
三种模式：`journal`（数据也记，最安全最慢）、`ordered`（默认，数据先落盘再提交元数据 → 不会出现"元数据指向空洞"）、`writeback`（最快，可能读到旧数据）。
**追问**："rename 是原子的吗？" → 同 FS 内是（目录项替换），所以"写临时文件 + fsync + rename"是配置原子更新的标准做法。

---

#### Q37 文件系统怎么防止碎片？ext4 和 XFS 怎么选？★★☆☆☆
**归属**：阿里、字节

**答**：ext4 用 **extent**（连续块记录，减少元数据）+ **延迟分配**（先攒再分配连续块）+ 多块分配器；XFS 用 B+ 树 + 延迟分配 + 并发友好（分配组 AG）。
选型：大文件/高并发/大目录 → XFS；小文件多/兼容性/快照需求 → ext4（或 btrfs 的 COW 特性）。

---

#### Q38 什么是 mmap？和 read/write 的区别？★★★☆☆
**归属**：腾讯、美团

**答**：mmap 把文件页映射进地址空间，读写直接操作 page cache（无需 copy_to_user），适合大文件随机访问、多进程共享。缺点：SIGBUS 风险（文件截断）、错误感知延迟（回写才知）、小文件效率不如 read/write、映射/解除有开销（VMA 操作 + TLB shootdown）。

---

#### Q39 df 和 du 结果不一致，为什么？★★☆☆☆
**归属**：阿里、运维岗

**答**：① 文件被 `unlink` 但仍有进程打开（`du` 不算，`df` 算）；② 稀疏文件（`ls` 大，`du` 小）；③ 硬链接被 `du` 去重；④ 已删除文件的挂载点被覆盖（未 umount 就删目录）。排查：`lsof +L1` 找 deleted 文件。

### 六、综合与场景题（9 题）

#### Q40 CPU 使用率 100% 怎么排查？★★★★★
**归属**：全行业（运维/后端）

**答**：见 14.3 场景 1。分层：`us`（用户态热点 → perf/jstack/pprof）、`sy`（系统调用 → strace）、`si`（软中断 → 网络）、`wa`（IO）、中断/kworker。注意"容器内 top 看到的可能是宿主机"。

---

#### Q41 服务器负载高但 CPU 空闲，为什么？★★★★☆
**归属**：字节、美团、滴滴

**答**：Linux 的 load 包含 **D 状态（不可中断睡眠）**。查 `vmstat` 的 `b`、`ps -eo state,pid,comm | grep D`、`cat /proc/*/stack`（需 root）。常见原因：磁盘/网络存储卡住、NFS 服务器无响应、驱动 bug、大量同步 IO。

---

#### Q42 内存持续上涨怎么定位？★★★★☆
**归属**：阿里、字节、腾讯

**答**：分层：① 进程 RSS（`smaps_rollup` 看 Anon/File/Shmem）→ 用户态泄漏（valgrind/pprof）；② 内核 slab（`slabtop`、`/proc/slabinfo`，dentry/inode 泄漏常见）；③ page cache（正常）；④ 碎片（`/proc/buddyinfo`）；⑤ 容器看 `memory.stat/current`；⑥ 检查 `mmap` 未释放、线程栈累积（每线程 8MB 虚拟 + 实际提交）。

---

#### Q43 一台机器能支撑多少并发连接？受什么限制？★★★☆☆
**归属**：腾讯、字节、B 站

**答**：不是单一上限：
1. fd 数（`ulimit -n`、`fs.file-max`）；
2. 端口（客户端受 65535 + 四元组限制，服务端不受）；
3. **内存**：每连接的内核结构（`struct sock`、收发缓冲 `tcp_rmem/wmem`）× 连接数 —— 通常是真正的瓶颈；
4. CPU：中断/软中断/协议栈处理；
5. `somaxconn`、`tcp_max_syn_backlog`；
6. 应用层（线程/协程数量、内存）。

**估算示例**：每连接 8KB 内核内存 + 应用层 20KB → 10 万连接 ≈ 2.8GB。

---

#### Q44 为什么容器里 free 显示的是宿主机内存？★★★☆☆
**归属**：阿里、腾讯（云原生岗）

**答**：`/proc/meminfo` 未做 namespace 虚拟化（procfs 只虚拟化了部分文件），容器读到的仍是宿主数据。正确做法：cgroup `memory.current/max`、`memory.stat`，或 `lxcfs` 挂载伪造的 proc 视图。

---

#### Q45 如何设计一个高性能服务器？★★★★☆
**归属**：字节、腾讯、美团（综合题）

**答**（分层）：
1. **IO 模型**：epoll/io_uring，主从 Reactor，非阻塞 + 边缘触发；
2. **线程模型**：Reactor 线程数 ≈ 核数（避免切换），业务放线程池；CPU 密集用绑核 + SO_REUSEPORT 多进程；
3. **内存**：对象池/arena 分配器（避免频繁 malloc）、零拷贝（sendfile/splice）、避免伪共享；
4. **锁**：无锁数据结构、per-thread 计数、RCU/读写分离；
5. **内核调优**：`somaxconn`、`tcp_rmem/wmem`、`tcp_tw_reuse`、`backlog`、中断亲和性/RPS；
6. **观测**：火焰图（on/off-CPU）、PSI、`perf c2c`。

---

#### Q46 什么情况下会触发上下文切换？★★★★☆
**归属**：阿里、字节

**答**：① 时间片用完（`scheduler_tick`）；② 阻塞（等 IO/锁/信号量，主动 `schedule`）；③ 被更高优先级抢占（唤醒抢占）；④ 系统调用返回用户态时检查 `TIF_NEED_RESCHED`；⑤ 中断返回时；⑥ 主动 `sched_yield`；⑦ 负载均衡迁移。
**追问**："`cs` 很高但 CPU 不高，为什么？" → 大量短临界区锁竞争、频繁 IO 唤醒、线程数过多；用 `perf sched`/`off-CPU 火焰图`定位。

---

#### Q47 一个程序从执行到退出，操作系统做了什么？★★★☆☆
**归属**：百度、小米、京东（综合）

**答**：shell `fork` → 子进程 `execve`（加载 ELF、建 mm、映射段、设栈、跳到 `_start`）→ 动态链接器 `ld.so` 加载依赖、重定位 → `__libc_start_main` → `main` → 运行（缺页按需加载、系统调用）→ `exit`（`do_exit`：释放 mm/files、通知父进程、变僵尸）→ 父进程 `wait` 回收。

---

#### Q48 内核态和用户态的"隔离"是怎么做到的？如果去掉会怎样？★★★☆☆
**归属**：华为、阿里（安全/内核）

**答**：靠 CPL + 页表 U/S 位 + IDT 门 DPL 三重检查；用户态无法执行特权指令、无法访问内核页。
去掉后（如 DOS、无 MMU 的 MCU）：任何程序都能改中断向量、直接访问硬件、一个野指针能改坏内核 → 无隔离、无稳定性、无多任务安全。
**延伸**：Meltdown 让"页表 U/S 位"失效（投机执行可读内核内存）→ KPTI 用两套页表隔离；Spectre 则是分支预测侧信道，缓解手段是 `retpoline`/`lfence`/`IBRS`。

### 16.3 高频"一句话答案"（临场救急）

| 问题 | 一句话 |
|---|---|
| 为什么用虚拟内存 | 隔离 + 抽象 + 按需 + 共享 + 超额分配 |
| 为什么要多级页表 | 只为用到的区域建表，省空间；靠 TLB 摊时间 |
| 为什么 fork 快 | 只复制页表并标只读，数据靠 COW 延迟复制 |
| 为什么系统调用贵 | 特权级切换 + 栈切换 + 保存寄存器（+ KPTI 切页表） |
| 为什么线程切换比进程快 | 不换 CR3、不刷 TLB（其余成本相同） |
| 为什么 epoll 快 | 把 O(n) 遍历换成回调，只处理就绪的 |
| 为什么零拷贝快 | 传页引用而非拷内容，省 2 次 CPU 拷贝 + 2 次态切换 |
| 为什么 write 不等于落盘 | 只写了 page cache，要 fsync 才到介质 |
| 为什么容器轻 | 只是 namespace+cgroup 约束下的普通进程，共享内核 |
| 为什么有软中断 | 硬中断要短且不能睡眠，耗时/可睡眠的工作推后做 |

### 16.5 面试答题的通用套路（针对操作系统类问题）

```
四步回答法（任何机制题都适用）:
  ① 一句话定位: "它是为了解决 X 问题而设计的 Y 机制"
  ② 机制拆解:   数据结构 + 流程（能画图就画）
  ③ 关键取舍:   为什么这么设计？代价是什么？（这一步区分中级和高级）
  ④ 工程延伸:   实际场景中的坑/调优/观测手段（这一步区分高级和专家）

反面案例（低分回答）: "虚拟内存就是把硬盘当内存用"（错，swap 只是它的一个可选项）
正面案例: "虚拟内存的核心是给进程独立的地址空间并用页表做翻译；
          按需分页只是它的一个策略，swap 又是这个策略的延伸" 
```

### 16.6 三句话总结整份文档

1. **一切皆是虚拟化**：CPU 用时间片虚拟、内存用页表虚拟、磁盘用文件虚拟、网络用 socket 虚拟。
2. **一切虚拟化都有代价**：缺页、切换、拷贝、锁、TLB 失效——**性能优化的本质就是减少这五种代价**。
3. **一切机制都为"并发下的正确"服务**：多核 + 抢占 + 乱序，让"看起来对"和"实际对"之间隔着原子指令与内存屏障。
